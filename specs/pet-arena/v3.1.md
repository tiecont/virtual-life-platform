## Banner and durable transaction contract

Permanent Standard S pool contains exactly the six Standard IDs with initial
equal positive integer weights. Limited misses select this pool, always an S.
Map S is excluded. Eligible Limited family candidate rates are0.8% base S,
soft pity from60, hard80, featured50% when not guaranteed. After a miss, the
next S in the same family is guaranteed featured. Reset pity on S; clear guarantee
on featured. Standard results never alter Limited state. Maximum160 applies only
to an eligible, continuously available configured Limited family.

The soft-pity curve is deliberately UNAPPROVED/null. Neither launch rates nor
lower-rank pools are finalized. Publication must reject missing curves/pools.
Publish every per-pull S probability and normalized per-Pet weight before any
real-money release. Validate monotonic probabilities, exact hard pity, positive
weights, effective dates and eligible source/rank. Admin uses reviewed immutable
versions, RBAC/step-up, CSRF, optimistic concurrency, audit and rollback.

Persist state by account+banner family, not transient banner ID. Rotations and
reconnects retain pity/guarantee under disclosed carryover. Pin banner version,
curve and pool to accepted requests. Single and ten pulls process the same
ordered state transitions. Use server entropy with durable request reservation,
request hash and account-scoped idempotency key; clients never choose RNG.
Retry of a committed key returns its exact ordered receipt; conflicting payload
rejects. Account/family/wallet locking serializes distinct requests. Atomic
wallet debit, pity, ownership, duplicate conversion and receipt either commit
together or do not change player state. A failed/reserved attempt cannot be
rerolled on retry. Test crashes before/after commit and lost acknowledgements.

First copy C0, seventh C6, eighth and later convert once into configured exchange
resources for approved tickets/items. Both S sources share the replay-safe ledger;
C-level never changes the maximum three stars. No client grants. Owner APIs/UI
show rates, details, pity, guarantee, transaction status and private pull history.

## Persistence boundary

This first PR adds source drafts and validation, not a gameplay migration or DB
import. The current schema permits only v2 and two skills; do not force these
four-skill v3 drafts into it. VL-130 supplies strict bounded runtime contracts;
VL-131 extends the Nest-owned journal additively with rank/source and versioned
catalog relations. Reuse VL-115 storage ownership/restore infrastructure without
waiting for unrelated publication completion. Preserve legacy rarity separately.

Import only validated complete manifests into an owned disposable DB first.
Stable catalog version plus SHA256 exact UTF8 file-byte hashes identify content;
whitespace changes produce a new digest. Same version/hash is a no-op under
concurrency; mismatched hash aborts the full transaction. Validate all foreign
keys, effect bounds, unknown fields and publication flags before writes. No
Unity/Rust direct SQL, no PUBLIC draft grants, no player ownership or purchases.
Actual PostgreSQL constraints, idempotence, corruption, restore and zero-grant
checks are required before claiming seed persistence complete.
