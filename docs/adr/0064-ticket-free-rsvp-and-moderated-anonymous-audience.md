# ADR0064 — Ticket-free RSVP and moderated anonymous audience

M19-04 reuses Events RSVP and Room admission rather than creating ticket inventory or a second room owner. Native Lounge RSVP is available for SCHEDULED/OPEN sets before their start;LIVE does not offer a new RSVP. A confirmed intent reserves neither admission,a chair nor stage permission. Unconfirmed changes are serialized and resolved with their original key. This UI does not promise an independent Stop for a not-yet-recorded RSVP. Known own confirmed intents retain a withdrawal path when the catalog/source becomes unavailable;historical confirmation is labelled as historical rather than current attendance. Identity changes clear this local history. Existing Library/Restaurant contracts are preserved.

Lounge world1.3.0 declares audience policy1.0.0;the scene stays1.0.0. Policy is a separate dependency-free contract to avoid a World/Travel/Room import cycle. Only public listed stage venues may declare it. Reactions are the finite Clap/Star/Wave choices,never free text,media,profile disclosure,score or client-controlled timestamps. Sending requires an actual current attached room visit,a current confirmed own RSVP,a LIVE listed event,current safety policy including mute/chat incident restrictions,and an open approved feed. No real operator is provisioned here.

The feed starts DISABLED. Only a current registered world-scoped moderator/safety-admin may open it while connected in the actual target room. Approval is bound to that original visit,world/policy version and at most five minutes,clipped by moderator grant,connected session and event expiry. A current event organizer or scoped moderator may MUTED/DISABLED it outside the room/world. Negative suppression ignores a stale expected version and advances the durable version even when already closed,so a delayed positive open cannot override it. Reopening is a new explicit moderated action with the current expected version. Exact old keys return current state rather than restoring an old mode.

Each room has a single small SQL aggregate with three visible counters and a separate accepted-total budget,at most twenty accepted reactions in a server-owned ten-second window. Mute/disable clears visible counts but preserves that budget;reopening within the same window cannot buy another twenty reactions. Review found this distinction after the first passing suite;the actual ten-person TCP wave case now covers mute/reopen while exhausted. Account-level SQL cooldown survives session changes/restarts:at least two seconds between accepted sends and at most five in a ten-second window. Persistent successful-receipt quotas also bound sends to120/account/hour and positive approvals to60/account/hour. Shared HTTP IP/session limits remain unchanged. There is no per-reaction broadcast or queue per spectator:reads return a small aggregate and native clients refresh explicitly. This bounds the implemented fan-out mechanism;production latency/CCU and wider emergency coverage remain M19-06 work.

Positive commands enter the Room source owner before sorted account locks,Events row and feed row. The currently approving moderator is captured before account locking and rechecked after row locking;changed references require a retry instead of late account locks. Durable counters,cooldowns and mutation receipts commit together. Every send checks current approval again after awaiting the receipt INSERT. A real SQL wait test exposed acceptance after a shortened moderator grant expired;approval now clips downward and post-wait guards reject and roll back. Original window boundaries also fence the final effect so an await cannot carry a reaction into a different window. Receipt replay cannot add another count or restore expired/muted authority.

Event cancellation/end clears counts and approval in the Event transaction. Shared block between organizer and approving moderator invalidates collaboration in the block transaction. Actor blocking an approver prevents that actor's further sends. Own RSVP withdrawal prevents new sends and makes old send receipts noncurrent;already anonymous aggregates expire with their window. Approval grant/session/source/world/safety loss ends the feed without automatic restoration. Fair maintenance checks twenty open feeds per batch on the three-second scheduler;positive commands independently reauthorize. Restart invalidates old visit proofs. Account erasure clears moderator source proof and closes its feed immediately through the deletion owner.

Anonymous snapshots disclose no names,actor IDs,moderator IDs,room/membership proof or per-person reaction list. Public-event lookup is filtered before room-proof checks so private UUIDs do not produce a different room-error status;an actual red/green case verifies generic404 and no header allocation. Small groups can still infer contributions;the UI states this before sending. Observations expire after at most three seconds;hidden/offline/source/identity changes invalidate them. Mute/disable is immediate at the server serialization boundary;other clients' previously observed numbers disappear on refresh or that short expiry. There is no claim of instantaneous delivery to every device. A local operation generation prevents held successful OPEN replies from restoring UI authority after a later negative action. Current staff permission is always checked again for suppression.

Additive0031 stores feed controls/aggregate,account cooldowns and append-only mutation receipts. Because0031 had already been applied locally,its checksum is preserved;additive0032 backfills and constrains the separate accepted-total window budget. Event/account FKs cascade own data;moderator deletion also clears JSON visit proofs. Own export is limited to100 command summaries without peer IDs or raw reaction choices. Send receipts and cooldowns expire after24hours;operator control receipts after90days. Cleanup removes at most100 rows per table/batch. Parent Events retention also cascades. A schema rollback is not required:close the feed and disable the local world/installation while retaining private history. Default real rollout flags remain OFF;this is not operator coverage,media clearance or public launch approval. Actual verification/failures and migration state are recorded in m19-audience-checks.json.
