# ADR0066 — Closed dating definition precedes private runtime

M20-01 audits the existing adult-provider/default-deny/hidden-world/presence/discovery/Events/travel/reporting boundaries before adding dating data. No real dating module,profile,match,date room,verification provider or operator signoff exists. Keep existing global dating hiding and public Events/invitation exclusion;do not scaffold over the shared owners or represent a boolean/18+checkbox as real verification.

Add a strict versioned `DatingPolicySchema` and `config/dating-policy.json` with literal closed-draft approval state,registered/current-reviewed-proof requirements,separate consent/private-data rules,finite two-person/timed/canned scope and provisional bounded retention. A dedicated `dating:check` validates the actual JSON plus Safety/rollout invariants within the root check. This is executable policy-definition verification,not an active eligibility service or cleanup implementation. No runtime endpoint,world,DB migration or public feature is introduced in this slice.

Policy1.0.0 cannot mark approvals true,install a provider,make global dating disclosure public,enable uploads/free text/media/payments or override independent Leave/mutual consent. The owner must supply actual reviewed verification/jurisdiction/coverage/privacy/appeal resources and explicit signoff in a later reviewed revision. M20-07 remains externally gated even if local runtime tests later pass. `DATING-GATES.md` records the pending signoff table and review/data-minimization requirements;it gives no legal-compliance or age-assurance certification.

The audit specifically finds that shared Room reporting requires a globally visible profile,while dating presence is hidden. M20-04 therefore needs a dedicated currently matched contact proof/Reports port with scoped private attribution. Never make a dating profile public to work around this boundary. Room.list also enumerates rooms after world authorization without a per-match filter. Current real dating access is denied because no module/provider exists;before any private-room installation,deny generic dating enumeration and bind every direct join/travel to the exact accepted pair. Adult eligibility alone cannot be room permission. Match-bound private admission/projection,atomic negative-consent withdrawal,private export/erasure and repeat eligibility/safety checks are future M20-02..06 work;model-only checks do not verify them.

There is no data migration or media. Rollback removes the unused draft model/checker while leaving all existing default-deny adult/hidden/discovery and release safeguards intact. Actual commands and scope are recorded in m20-gates-checks.json. No real human approvals are fabricated;public/pilot flags stay OFF.
