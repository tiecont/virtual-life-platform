# ADR 0004 — City identity and private browser sessions

Status: Accepted local implementation, 2026-11-02. M03 guest/privacy slice verified; registered upgrade is next, not yet implemented by this checkpoint.

City owns independent accounts/profiles/private choices/sessions. Cookie `city_session` is host-only in local HTTP; production `__Host-city_session` has Path=/, Secure, HttpOnly, SameSite=Lax and no Domain. @fastify/cookie signs opaque tokens with an environment-only >=32-character secret. DB stores SHA256 token hashes, never raw tokens. CSRF is an HMAC-derived token returned only on authenticated self endpoints; all writes require exact Origin, and authenticated writes also require CSRF and UUID Idempotency-Key. Secret changes invalidate cookies; multi-key graceful rotation is future operational work, not claimed.

Guest POST accepts a client-generated random UUID requestId for retry (never URL, analytics or logs). This key is temporarily a bootstrap capability: keep it in transient memory, discard after success, never publish it. Server adds a random nonce and HMAC derives the session token; the DB holds only keyed request/fingerprint, nonce and token hash. Concurrent retries create one identity. An authenticated existing city session cannot be switched to a client-selected account/name by bootstrapping again. After expiry/purge a reused key creates a fresh account with a fresh server nonce; old cookies cannot recover it. Deleted/revoked bootstrap within its lifecycle is rejected. No account linking by display name or avatar.

Session rotation serializes by old credential; retries with the same old cookie/key reproduce the new token only while that target session is active. Old cookie cannot read/write or start a different rotation. Logout and deletion have duplicate semantics. Generic profile/privacy request receipts last 24h; session/bootstrap receipts last their bounded lifecycle. HMAC fingerprints avoid storing an unkeyed digest of future password-bearing payloads. Notifications fire only after commit and expose server account/session IDs to trusted consumers; M06 must bind live sockets and test actual revocation. Every request still checks authoritative DB expiry/revocation.

Private choices are a separate table, default presence hidden and analytics false. Dating presence is never globally disclosed even if global presence is public; dating override can only be hidden. Public profile uses explicit ID/name/avatar allowlist. Own export excludes tokens/CSRF/other identities. Deletion cascades own data and retains only a 24h keyed anonymous retry receipt. Five-minute maintenance purges expired sessions/bootstrap/receipts and orphan guest accounts. Registered-account retention will differ and must be documented with upgrade. Retention is local policy, pending public operator/legal review.

Eligibility is a server service interface, not client age/role input. No adult provider or restricted release approval is installed; unknown/underage/self-attested accounts are denied restricted access. Presence filtering applies bilateral blocks/friendship and per-world choices. M04/M06/M09 must wire these interfaces to actual social/socket/travel entry points; those features are not verified by unit-policy tests.

Legacy compatibility: Deadline token/cookie, Maid schemas and avatar vocabularies differ. Tests reject old cookies, body formats and forged authority. No automatic migration/proof exchange exists yet. M15/M16 require explicit possession proof, stable revisions and live compatibility tests; original apps/DBs remain untouched.

Migration: additive 0002_identity.sql in city DB only. Rollback disables identity route/UI, leaves original apps unaffected, and restores only from an approved tested backup in shared environments. Never down-migrate or reset developer/legacy DBs automatically.
