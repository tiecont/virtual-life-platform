# ADR0084 — Park groups use existing consent and travel

Status: Accepted;M24-04 locally VERIFIED from 11dbef0. Evidence: `../agent/evidence/m24-groups-checks.json`.

Reuse GroupInvitations for two-to-four independent friend offers and M09's durable root/child receipts, current consent/block checks, finite expiry and authoritative travel admission. A Park gathering does not create another party database, reserve room places or transfer anyone on acceptance. Each recipient uses the existing invitation inbox to accept or decline and separately confirms their destination. The sender also chooses travel independently; available capacity can split a group.

A ParkGather wrapper supplies current friends, world catalog and invitation revision while the visitor has an active Park source. It subscribes to relevant changes on the existing Room socket and offers manual refresh; it creates no second transport. Unknown reads clear private choices and disable positive sending. Keep the shared GroupInvitations component mounted through a temporary read outage so its canonical unknown-outcome keys survive; reset the wrapper on source/session changes so leaving cannot be reversed by a late offer reply. Existing committed offers remain manageable in the inbox and are not implicitly cancelled by closing the panel.

Extend shared GroupInvitations with an optional optionsKnown flag, defaulting true for its existing inbox caller. Unknown choices must not be described as an empty friend list. When fresh friends exclude a previously selected contact, prune that selection; server-side rechecks remain authoritative. No forced contact, membership, staff role or restricted-world access follows from UI choices.
