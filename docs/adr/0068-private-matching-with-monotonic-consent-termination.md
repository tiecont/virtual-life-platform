# ADR0068 — Private logical matching and monotonic negative consent

M20-03 extends the synthetic-only private profile with an explicit bounded queue,opaque two-person proposal and separate acceptance per participant. No Dating World,Room,chat,peer profile projection,contact details,public provider or real participant operation is installed. All real approvals/rollout remain OFF and M20-07 remains externally blocked. A logical ACCEPTED lease is not an active date or authority to join a generic room.

The matcher consumes only finite encrypted-profile choices via an internal owner port:both participants' preferred topics must overlap the other's offered topics and their calm/lively/either pace must be compatible. It does not inspect general nickname,gender,birthdate,location,friends count or popularity score. Clients cannot select a peer or supply age/roles/eligibility/score. Responses contain only own queue/consent/state,an opaque proposal UUID,version,own acceptance bit and bounded deadlines;even ACCEPTED exposes no peer account IDs,alias or topics. This slice makes no fairness/suitability/human age-assurance certification.

Migration0034 adds a consent revision,one enrollment primary key per account,private proposal and HMAC-only mutation receipts. An enrollment is either queued or linked to exactly one proposal,so one account cannot hold two active allocations. A queue lasts at most120seconds,proposal45seconds,accepted logical lease at most300seconds clipped by original participant session/proof/profile authority. The proposal SQL deadline cannot exceed345seconds from creation. Both explicit current original-session acceptances are required;parallel equal-version acceptances may yield one409 requiring refresh,then the other can choose. Exact-key retry returns current state after fresh authorization;no old projection restores consent. Original proposal deadline is fenced after all awaited receipt/view work even when second consent would extend the logical lease.

Positive reads/joins/accepts and bounded maintenance take a PostgreSQL advisory transaction mutex **before** capturing the active actor proposal/at most20queued candidates and then locking every captured account in sorted order. Capture never grows after account locks. The mutex serializes candidate selection with other positive writers;negative operations deliberately do not take it. Profile/session/proof/safety/current consent and bilateral blocks are rechecked under account locks before touching proposal rows. Profiles are accessed before shared proposals,not while waiting for new account authority. The single-process deployment is unchanged;the SQL mutex does not implement distributed Room ownership or high-throughput matchmaking.

Profile save/withdrawal/expiry,account erasure and bilateral block integrate in their existing owner transaction. Negative callbacks obtain no matcher mutex or peer account lock. They read the current own enrollment,lock/terminate its shared proposal first,then delete its linked enrollments and advance the own consent fence where appropriate. A negative operation handles at most one active proposal per account. A block callback closes only the actual blocked pair;unfriend alone is not dating withdrawal. It never reconstructs prior consent when unblocked. A profile edit conservatively withdraws its queue/proposal/accepted lease even if topic values remain compatible. An injected shared-close failure rolls back the profile/block mutation too.

This order avoids an account→global-mutex inversion or peer-account acquisition inside profile/Identity/Social callbacks. Positive work may hold captured account advisory locks while a negative callback deletes a peer enrollment;it cannot already hold the shared proposal and wait for an uncaptured account. Atomic account deletion closes the shared allocation before FK cascades remove history. Concurrent Stop/accept/block/profile-change/delete tests exercise these paths against actual SQL/network calls;the design still requires review before adding date-room or continuation callbacks with additional locks.

Join uses an account/session/current-profile/current-consent HMAC grant valid<=30seconds. Twelve new join commands/account/hour are durable,including no-op fresh-key joins while already queued;exact-key retry adds no receipt or grant renewal. Global enrollment count is bounded100,search scans20with a monotonic checked-order sequence,rotating inspected candidates rather than using frozen timestamps. Private refresh may pair an already consenting queued actor;it never enrolls a NONE actor or requeues an expired/declined/ended one. No general socket broadcast/notification is emitted;manual own observations expire<=5seconds. No aggregate queue length is disclosed.

Stop and decline need authenticated current session,Origin/CSRF/key/strict body but no positive key/proof/profile/feature eligibility. Stop advances own negative consent and removes the current queue or terminates both proposal allocations. Decline requires an own proposal handle and closes it even if the peer's acceptance won immediately before it;no automatic requeue. Negative receipts are bounded200/account/day,retained90days;overflow still stops without another receipt and may strengthen the fence on retry. Same-key negative retry confirms its historical request rather than undoing a later explicit new choice. The UI labels it recorded and asks for a fresh observation. Positive grants expire long before negative fences/history can be purged.

Recovery checks20open proposals plus20queues/batch in sequence order on the existing3second service loop,validating original sessions/current profile revision/proof/safety/blocks and immutable deadlines. Revocation,session rotation/logout,profile changes or expiry end authority without requeue. Process restart preserves durable queues/proposals only while their original persisted session/profile/proof and deadline remain valid;it grants no room or reconnect consent. Ended proposal history/positive receipts keep24hours;negative receipts/consent fences keep90days with100row cleanup per table. Consent cleanup never deletes an active enrollment. Own export is bounded100command summaries with no proposal ID or peer linkage;account FK erasure removes owner rows and shared proposal history. Draft values are checked against the fixed prototype implementation,not hot-reloaded operational approval.

The private page adds native explicit queue/accept/Stop controls. Generation fences and aborts discard held late positive replies after Stop. Identity checks precede requests;socket revocation/disconnect,hidden/offline and observation expiry clear state. Unknown outcomes preserve the exact original key/body in component memory;no private data/grants go to URL/storage/global notifications. Stop remains independent during a pending positive request and after eligibility loss;the separate profile-withdrawal page also invalidates matching. Native controls reuse the existing44px styles. No autoplay,media or free-text surface is added.

Profile withdrawal must also invalidate matching observations in the same page. A client wrapper remounts the matching panel at withdrawal start,aborting pending requests and discarding their generations;positive matching is suppressed while withdrawal is unconfirmed. Independent Stop remains available. An old-artifact browser reproduction exposed a held committed queue reply restoring QUEUED after profile withdrawal on mobile,despite correct backend removal;the regression is retained and the wrapper build is verified separately. This is reproduction against an earlier artifact after the source fix was written,not red-before-code evidence.

Actual acceptance/failures/commands are recorded in m20-matching-checks.json when collected. The initial route404 red,compile check launched before package build completion plus explicit optional-row type correction,and unused-type lint failure are retained. Migration is additive;rollback disables positive prototype configuration while preserving current Stop/withdraw/export/erasure handlers and SQL history. Do not run an older enabled private prototype against rows it cannot terminate. M20-04 must independently fence exact-match Room admission/directory and add private matched-contact reporting before any date communication;adult eligibility alone is not private room permission.
