# ADR0127 — Durable admission transactions under the existing single room owner

Accepted for N09-02 local preparation, 2026-11-06. No runtime activation or capacity increase.

The reference model in ADR0126 cannot establish atomic grants across retries. Add migration0044 and an unwired AdmissionStore port using the existing PostgreSQL and identity/room-owner boundaries. One policy row serializes queue mutations and grants. Queue order is a unique increasing sequence: duplicate enqueue preserves age and TTL, missed/expired tickets must requeue at the tail. One account primary key makes WAITING/RESERVED/ACTIVE/RECONNECT_GRACE disjoint. Active+grace+reserved is counted from rows; target governs new offers and the database also rejects a hard-bound violation. A pending hard reduction settles only after occupancy fits. No active player is expired by wall clock.

Commands derive the actor from a live session, take the existing canonical identity account lock before the policy lock and reauthenticate before commit. Offer allocation reads the identity-owned availability hint without acquiring an inverse account lock; claim performs the stronger locked check. The policy row already serializes allocators, so head selection does not pin an entry row. The offer receipt acquires account FK custody before the entry update, avoiding an inverse account/entry row-lock cycle with privacy deletion. Client input contains no actor/capacity/clock authority. Request fingerprints and changes commit together; replay reads canonical current own state, including null after release/expiry, rather than replaying an old authorization. Receipts retain seven days, new actor commands are bounded to30/minute and cleanup processes100 rows/table/transaction. Queue ceiling10000 and TTL bounds are technical guardrails, not measured sustainable capacity.

Owner checks before work, before commit and after acknowledgement use the existing dedicated advisory-lock guard. A stable epoch belongs to that owner lifetime; multiple adapters in that process must share it. Replacement owner recovery removes at most100 obsolete occupied records per transaction and admits nothing until reconciliation finishes; waiting order remains. This is valid only because the previous single owner's in-memory memberships ended. It does not implement multi-owner fencing or restore room/social consent. Pool checkouts, requests, statement/lock waits and transaction work are bounded; late/broken clients are destroyed, and this service never ends the shared pool.

The first43 migrations remain byte-identical. Strict44 readiness requires a44-aware qualified rollback image or an independently reviewed compatibility window. Do not down-migrate or relabel an old strict43 image compatible. Production migration, runtime route/room/travel hooks, native auth and operator cap updates are outside this slice. Keep the feature unwired, hard/target0 and paused until subsequent gates establish integration and fresh capacity evidence.
