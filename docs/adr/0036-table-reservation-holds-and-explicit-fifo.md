# ADR0036: Virtual table holds, admission check-in and explicit FIFO consent

Status: Accepted local implementation; commands recorded in m12-reservations-checks.json. Date:2026-11-03.

Events and table bookings share the event transaction boundary. An optional world eventPolicy.reservations declares original virtual resource keys/capacities, maxPartySize, holdSeconds1..300 and disabled/FIFO waitlist. Trusted scheduling may select a declared resourceKey; omitted keys retain M12-02 one-place RSVP behavior. Table slots use [opensAt,endsAt) and cannot overlap for the same world/resource. The existing per-schema/world PostgreSQL advisory lock serializes overlap validation and schedule creation; adjacent windows are valid. No public table provisioning route, real-world address or external restaurant inventory exists.

A table slot reserves the entire virtual resource for one party, bounded by event and resource capacity. RSVP is rejected for table slots so a client cannot mix two allocation systems or partially oversell the table. A partial unique SQL index permits one HELD/CONFIRMED/CHECKED_IN booking/event. All hold/confirm/cancel/waitlist operations take sorted actor/organizer account locks then the event row lock before touching reservation-owned tables. EventService supplies metadata/transaction ports; reservation code does not read event repositories directly. Existing event observations invoke a trusted reservation observer inside the same transaction. No world-specific Restaurant code is copied.

POST reservations accepts only schemaVersion,eventId,partySize and requires auth/Origin/CSRF/key. It creates a server HELD record with deadline min(now + configured TTL,startsAt). State/deadline/schedule are snapshotted durably. Exact retries observe their original record, including after expiry/replacement; new keys cannot extend an existing hold. Confirmation must precede the original deadline. Relevant operations and fair existing event maintenance observe expiry under the allocation lock, releasing uniqueness before another claimant inserts. Server rollback is rejected; receipt insertion failure rolls back business effects. Commands are bounded30/minute,60/hour and five future active allocations/account; HTTP limits also apply.

POST reservations/:id/check-in requires confirmed booking and an actual connected matching session/epoch/room/membership in its world, within [opensAt,checkInClosesAt). Room owner authorization wraps the event transaction, and the room/world validity guard is checked again after awaited SQL before commit. A forged/full/stale room is not admission. Failed check-in preserves an unexpired confirmed booking; a late booking expires without attendance. Exact check-in receipt retries after restart may privately observe historical CHECKED_IN but never recreate room membership. This is the existing single-owner contract, not distributed fencing. PartySize is a declared virtual party count; this slice admits only the authenticated booking holder and does not force other accounts to join or guarantee physical group seating. Scene/seat-to-table routing remains the actual Restaurant adapter in M18.

FIFO is explicit consent, not automatic booking. POST reservations/waitlist records a bounded private entry for at most min(five minutes,startsAt); at most50 waiting/event and five/account. Once the slot is free, only the first unexpired entry can explicitly POST a hold with its original party size. That changes WAITING to CLAIMED but leaves the booking HELD until explicit confirmation. Later claimants cannot jump the queue. Expiry/withdrawal/block releases consent; exact old keys cannot renew it. No unsolicited offer, auto-confirmation, queue participant list or indefinite slot hold exists. A sanctioned head may delay the queue until its short deadline; moderator queue operations remain M12-04.

Own GET/list/export are private and bounded50/100 with truncation, with elapsed states projected for export. Cancel/leave-waitlist remain available after world closure/block and return only own metadata. Organizer block cancels outstanding booking/queue consent in the social transaction; trigger failure rolls both back. Participant/account erasure cascades booking/queue/receipts, and event retention cascades its children. Natural end retains historical checked-in attendance; unserved reservations expire. Event cancellation observer releases outstanding allocations; the authorized cancellation endpoint/notices still belong to M12-04. No automatic reports, sanctions, progression or rewards are emitted.

Migration0020 adds optional event resource metadata and reservation/waitlist/mutation tables with FKs, bounded time/party checks and unique active slot ownership. Existing rows retain RSVP semantics. Rollback disables reservation policy/adapters while retaining tables; no destructive down or legacy mutation. No actual table UI, real Restaurant integration, party seating guarantee, public event activation or new media rights is claimed. Calendar attachment in M12-02 currently remains RSVP-only. All real flags OFF; retention/operational review and higher-wave release gates remain.
