# ADR 0056 — Restaurant bookings and voluntary room-bound parties

Status: implemented locally; verification is recorded separately in m18-booking-checks.json after commands finish. No public approval.

Audit confirmed Events owns time slots, whole-table holds, SQL uniqueness, expiry, confirmation, private history and holder check-in. Restaurant consumes those APIs and its two declared table resources. It does not copy an allocator, query engine tables from a world package, create events automatically or provision organizers. A resource has one party/time window across this world's instances. Room/chair admission remains independent; a booking does not promise a room instance or force a chair claim.

A numeric partySize proves no peer attended. Migration0026 adds reservation-owned attendance consent, bound to an account/owner epoch/room/membership, and a per-account withdrawal revision. After personally checking in, the holder explicitly opens a listed party to current visitors in that room. Each guest independently joins with their own authoritative visit and observed revision. Counts disclose no account list and represent connected, session-valid, safety-eligible consenting visitors. The holder is included only after opening. All current visitors in that room may observe a published aggregate; small groups may infer participation. This separate explicit disclosure is not global profile presence or analytics consent. Private parties/invitations remain M18-05.

Sorted account locks and the existing event-row transaction serialize allocation, reconciliation and receipts. SQL enforces one IN membership/account and reservation/account uniqueness. Each reservation permits at most64 distinct membership histories; projections bound20own/current parties and100own export records. Existing mutation limits30/minute,60/hour apply to party changes, alongside request/session limits. The room owner supplies current visit proof; shared safety and attached session validity are checked. Offline/invalid members are excluded and reconciled on observation; disconnect may require fresh voluntary join even after grace reconnect. Restart changes the epoch; retained history grants no current attendance.

Open/join carry expectedRevision. Global stop increments the account revision and atomically leaves its membership/closes its hosted parties without needing catalog, room or enabled world. It can win before a slow open/join, rejecting older input, or withdraw after that input commits. Stop is semantically idempotent; repeating it can advance the private revision again. Exact receipts only return canonical private state, never enroll. Leave/close/block invalidate pending consent. Bilateral block revokes affected participation; a holder block conservatively closes its party. Social rollback includes these effects. No free text or external contact data are stored.

Event cancellation closes participation and includes consenting guests in the existing private recipient snapshot. Natural end retains CHECKED_IN booking history but separately closes the party/revokes consent; an actual failing integration test caught this distinction. Account/event deletion cascades members/revisions; existing90day event retention owns cleanup. Own export includes bounded consent history without peer accounts or visit proof. IN in historical export denotes stored consent, not verified present attendance. No reward, automatic report/sanction or external message is introduced.

The UI uses strict owner schemas, independent read outcomes,30second booking/catalog and5second group observations,8second deadlines, identity/visit/hidden/offline invalidation and exact-key uncertain retries. Independent stop remains available during pending writes/catalog outage. It aborts obsolete rendering; server revision ordering guarantees withdrawal. Hold, confirm, personal check-in, publish and guest join are separate native actions. Empty schedules require a successful empty response. Own cancellation is offered before check-in;afterward stop withdraws group consent while CHECKED_IN history and its slot allocation remain until slot end/organizer cancellation. Native UI tests caught and removed the earlier no-op cancel button without weakening the existing lifecycle.

Compatibility: existing event/reservation wire shapes and eight-column mutation inserts remain valid. New party contracts/endpoints are prerelease additions. Room check-in callbacks receive an additive visit-proof port; existing callbacks remain compatible. Actual staff/courses/private-table policy remain M18-03..06; no real flag/session/grant changes.

Rollback: disable the local Restaurant flag/module and stop the process; retain additive0026 data/journal. Dropping consent tables/columns or rewriting the operation constraint can destroy history/reject retained receipts, requiring reviewed backup/data decisions. No destructive rollback SQL is executed. Review older binary/database compatibility before any deployment rollback; an additive migration alone does not prove it. No deployment, legacy copy or remote repository action occurs.
