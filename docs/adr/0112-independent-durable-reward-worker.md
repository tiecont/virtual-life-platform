# ADR 0112 — Independent durable reward worker

Date: 2026-11-06. Status: accepted; actual local checks passed for N05-05.

Provide a separate `worker.ts` composition root for the existing hospitality completion outbox. It builds into the API artifact and runs as a separate Node process. It never calls createApp, constructs RoomAuthority, listens for HTTP/socket clients or runs migrations. Worker configuration requires an explicit worker role, database and enabled progression policy file; it does not require session, media, dating, evidence-encryption or operator secrets. Existing real defaults remain API dispatch and disabled progression, with no policy file.

Extract ProgressionLedger from ProgressionService and canonical account transaction locks from IdentityService. API/focus/correction interfaces keep their existing adapters and use the same implementation. Keep reward assessment, account ordering, eligibility reads, ledger/source uniqueness, entitlement synchronization and effect/delivery receipt transactions. Worker eligibility reads the current incident/sanction policy inside the transaction. The worker imports only the ledger/account-lock/job ports, not the session/focus/room services. A runtime-import graph check and negative fixtures enforce this boundary in architecture verification. Static analysis trusts installed dependencies and does not claim a security sandbox.

The API retains all room-bound maintenance. Its default constructor/role retains the original retry/backoff behavior, including the capped attempt counter without automatic quarantine. Only explicit external dispatch changes main's periodic chain: hospitality maintenance still runs, but outbox dispatch is left to the worker. API and worker must use the same immutable policy file during that cutover. This configuration is deployment-owned, not a player or admin toggle. There is no automatic handover, global policy-hash registry or production activation in this task.

The worker passes a bounded retry policy (default30 attempts, allowed1..30), using existing retry rows as quarantine metadata. No new migration or parallel queue is needed. The existing20-event-per-consumer batch, transactional locks, per-consumer receipt, retry timing and bounded counter remain. Quarantined work stays durable until explicit retry, eligible retention or identity deletion; it is not marked delivered. CLI inspection returns at most20 metadata rows without account IDs or payloads. Retry requires the observed event/consumer/attempt count/due time, locks accounts and the outbox row, and never clears an already committed receipt. Comparing the due time also rejects a stale observation of an earlier poison cycle with the same attempt count. This is optimistic trusted control, not an authenticated/audited admin endpoint or a permanent command idempotency ledger; N07 owns that boundary.

Each batch validates the image-bound schema compatibility policy read-only, before invoking jobs. Unknown checksums/metadata/history stop delivery; the worker does not repair the journal or migrate a database. RuntimeLifecycle tracks jobs and keeps this process alive without an HTTP listener, stops new scheduling on SIGTERM/SIGINT, awaits admitted work/outbox close, then closes its pool within the same12s failure budget. Main's timer reference behavior is unchanged. Batch failure can retry later; batch-complete is a completion observation, not proof the whole queue is empty/healthy. Quarantine, backlog and metric freshness remain visible concerns for N07/N08.

The executable worker gate builds the API first and uses the actual compiled entrypoint. It covers concurrent workers, a real SIGKILL at a deferred PostgreSQL COMMIT after effects, poison quarantine/retry, schema refusal, fresh safety restrictions, API-role cutover and a long-running worker surviving API-owner shutdown without acquiring that owner. PostgreSQL can commit after the client dies; restart resolves that uncertainty through durable effect/receipt uniqueness rather than assuming rollback. Broader focus/hospitality regressions remain mandatory for the shared extraction. The initial missing build prerequisite, boundary failure, lint finding and stale-retry regression remain recorded.

Rollback: drain/stop workers first, retain the same schema and policy, then return API dispatch to its verified default role. Do not launch mixed-policy consumers. Legacy API dispatch may retry rows a bounded worker quarantined; inspect those rows before deliberately reverting. Never delete delivery receipts or restore revoked consent to force a retry. No room memory or owner state moves into the worker, and no production/public/store release follows from these checks.
