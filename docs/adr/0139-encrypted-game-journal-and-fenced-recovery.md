# ADR 0139 — Encrypted game journal and fenced recovery

Status: implementation candidate; N15-04 final verification pending.

N15-03's ephemeral waiting consent cannot authorize durable game state on its own. Add SQL0047 without editing the previous46 migrations. `engine_game_matches` owns a versioned encrypted state/seed, participants bind the original account/session/membership/seat, and `engine_game_active_claims.account_id` is the durable unique claim across all modes/tables. A partial unique index also bounds one active match per exact owner epoch/room. Request receipts and terminal results are unique; outbox rows contain recipient/version hints, not private views. No progression rewards or new RoomAuthority are created.

The journal receives an internal admission proof from the existing lobby's actual ready group. HTTP input cannot supply members, sessions, roles or a proof callback. Every participant must have independently consented and readied the same generation/version. The host cannot deal on behalf of an unready account. Readiness is consumed conservatively before COMMIT; failure or lost COMMIT acknowledgement requires new readiness for a new start, while the same committed start key reconciles its existing match.

Identity account locks are sorted and acquired before match row locks. Identity freshness, all original sessions, room membership, world/mode availability, pairwise blocks, safety and the original deadline are rechecked after waits before COMMIT. Fresh room observation occurs before taking SQL account locks; the final membership/registry fence is synchronous, outside the global RoomService queue. Re-entering that queue while holding identity locks could deadlock against an existing safety mutation waiting for those locks. RoomAuthority's existing dedicated connection supplies owner assertions. No game DB work is held inside the room queue.

Every accepted command persists one revision and a receipt in the same transaction. An identical key returns the receipt version plus an authorized current own projection, without applying the reducer again. Changed input conflicts; rejected commands have sanitized stable receipts and no effects. The pure core remains deterministic and contains no DB/network/system entropy. Server entropy is generated once for initial state and retained encrypted. Concrete rules/factories remain absent in normal composition; only a guarded disposable local test composition can inject the synthetic persistence adapter.

AES-256-GCM uses a dedicated game root and HKDF subkeys. AAD binds key ID, match, generation, owner epoch, mode, rules version and revision. Seeds, hands, roles, target and rule state are inside ciphertext; public commitment, opaque identifiers, status/version/deadline and membership proofs are metadata. Command fingerprints use a separate derived HMAC key. Keys never enter receipts, outbox, client DTOs, logs or repository configuration. Missing/wrong keys fail closed. Key rotation is not automatic: a key ID/secret mismatch requires deliberate custody recovery or a truthful abort.

Pool checkout, SQL statement/lock and total transaction waits are bounded. Late checkout clients and timed-out/in-flight clients are destroyed exactly once. A committed transaction with a lost reply remains ambiguous to that caller and is reconciled through the durable receipt; it is not declared rolled back. Private replies are withheld until a fresh owner/session/policy/membership check after COMMIT. Only committed recipient hints are stored; notification delivery and reconnect UI remain N15-05 work.

Recovery examines at most10 active matches per pass and rotates healthy rows. An old epoch, overdue deadline, missing session/visit, block/ban/closure, unavailable mode or lost/corrupt key aborts truthfully, clears claims and destroys ciphertext without declaring a winner. It never silently resumes hands after an owner change or impersonates a timed-out player. Starts/commands stay closed until an initial bounded recovery pass finishes. The opt-in API main process schedules recovery; the separate durable worker does not construct a room owner. Throughput/recovery-time qualification is still N19 work.

Block between actual coparticipants aborts in the existing social transaction. Erasure always uses the journal privacy owner, even with storage flags/key absent, to destroy shared ciphertext and release active claims before account cascades. Session IDs are opaque proofs without a cascading session FK: session GC must not silently free an active account claim. Exports contain bounded own match metadata and no peer/private state. Historical receipt/result retention remains a privacy/release review item; no proposed legal duration is activated here.

Rollback turns off local controls and keeps the additive schema. A separate reviewed checksum window lets the archived46 API run on47; strict defaults still refuse unknown suffixes. Actual archived-source rebuild, browser/socket compatibility, retained ciphertext/claim rows and roll-forward abort must be exercised. A disposable `pg_dump`/encrypted archive/`pg_restore` drill must prove separate archive/game key custody and keyless abort. These are local tests, not production deployment, operated backups, final game rules, physical-device or public release approval.

The crash fixture also uses an actual child API process and TCP room visits. After one durable turn it blocks the next receipt insertion in PostgreSQL, kills that exact owned process with SIGKILL, then verifies the unfinished turn rolled back. A new owner preserves the earlier receipt, destroys old secrets and releases claims through an abort. No public test endpoint or alternate room owner is introduced.
