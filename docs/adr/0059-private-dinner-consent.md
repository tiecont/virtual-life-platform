# ADR0059 — Reservation-owned dinner offers and restricted party disclosure

Status: accepted and locally VERIFIED for M18-05. Public activation remains OFF. Actual commands/results: `docs/agent/evidence/m18-private-checks.json`.

The existing event invitation API belongs to an event organizer. A diner holding an operator's virtual table slot is not an organizer. Restaurant consumes a reservation-owned dinner offer instead of obtaining scheduling or moderation privileges. The existing Social/Invitation owner port supplies current friendship, bilateral blocking and the recipient's default-OFF invitation preference. No world package reads another domain's tables.

An explicitly opened party has `room` or `invited` visibility. The default remains `room`; an absent input field retains its previous fingerprint and response shape. Changing audiences revokes existing guest attendance and offers before publishing the new audience, increments the holder's withdrawal revision and requires each guest to choose again. Invite-only means restricted party membership and aggregate counts. It does **not** hide the shared room, isolate physical chairs, create private chat, conceal the listed table schedule or authorize a private room. Both UI and documentation disclose this distinction. Uninvited current-room readers receive neither private party IDs/counts nor a private-existence truncation signal. Catalog/discovery continue exposing only their original listed schedule fields, never reservation/offer/roster identifiers.

Only the checked-in holder in the original connected visit can offer their open invite-only party to a currently eligible friend who permits invitations. A durable offer has PENDING/ACCEPTED/DECLINED/EXPIRED/CANCELLED phases. Response TTL is at most120seconds, clipped to check-in close; accepted permission ends at check-in close. Acceptance only grants restricted party viewing/join eligibility. It allocates no RSVP, room, chair, attendance or travel intent. Travel has its own explicit review and capacity/access check. A guest must then choose Join in the actual holder room. A room UUID in an accepted offer is a public destination hint, never authority.

Every action authenticates its own actor, uses Origin/CSRF and durable idempotency. The room owner is acquired before sorted participant account locks, event and reservation headers. Header-before-members ordering matches the existing scheduler/Stop/contact withdrawal. Accept/offer/mode changes revalidate current consent and server deadlines. Receipt failure rolls back the accompanying mutation. Terminal receipts cannot revive permission. Sender retries require a current visit; response/withdrawal receipts remain private historical results. Host loss/restart, expired sessions, flags/safety and check-in close prevent current access regardless of retained historical ACCEPTED state. Observation reconciles invalid attendance; no automatic enrollment on reconnect.

Block/unfriend, recipient opt-out, sender cancellation, recipient decline, audience change, party closure and independent Stop revoke active offers/guest attendance in the owning transaction. Opt-in/unblock/re-friend cannot resurrect old offers. Stop remains available outside the room/world and while another response is pending. Existing event cancellation notices include pending/unexpired and accepted offer recipients. Offer metadata requires a current eligible connected holder and current public-world disclosure; unavailable metadata remains null. Inbox refresh is manual, snapshots expire after30seconds, party counts after5seconds. There is no immediate notification or realtime privacy guarantee for already observed data.

Bounds:64offer history per reservation,50pending offers per recipient,12new sender receipts/hour,30mutations/minute and60/hour per actor;20inbox entries and100own export entries with explicit truncation. Parent event90day retention and account/event FKs cascade offers/receipts. Export contains own receipt/direction only, not peers, room proofs or fingerprints. The shared request budgets stay unchanged. These are local abuse controls, not a production spam certification.

An immutable own contact reference can be reported for24hours without entering a room or revealing the counterparty's profile. The Reports owner resolves subject/world from the owned offer, encrypts the optional note and minimal invitation/reservation references, and returns its existing private receipt. Staff require existing registered, scoped, assigned grants. The new evidence provenance explicitly supplies no room proof; room-eject rejects it. Other decisions still require authorized human review, existing severity/duration policy and audit. Reports create no automatic sanctions. Offer-based Block privately resolves only an actual own counterparty through the existing Social API. Generic actual-room report/block controls remain available separately.

Migration0029 adds visibility and two reservation-owned tables/indexes. Old generic `room` payloads/results keep their previous shape; clients displaying new invite-only fields and the new report provenance must upgrade together. Rollback: disable local Restaurant, withdraw active consent using existing owner controls and retain additive data; do not run destructive downgrade. No real operator, remote operation, license, public release or legacy adapter is supplied by this slice. Actual commands/results are recorded separately in `m18-private-checks.json` after verification.
