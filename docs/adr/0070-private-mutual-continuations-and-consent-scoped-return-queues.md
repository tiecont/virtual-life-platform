# ADR0070 — Mutual private connections and fresh return consent

Status:M20-05 implemented for the closed synthetic prototype;final verification is recorded separately in m20-continuation-checks.json. This decision grants no real adult/provider/operator/legal/pilot approval. M20-07 stays BLOCKED_EXTERNAL.

The concrete value is to keep one private connection choice after an actual ended conversation,and meet again only when both participants independently choose another round. A unilateral like authorizes no contact,partner projection or notification. The peer's NONE view must remain indistinguishable before/after that unilateral choice:own revision/version only,no peer liked bit,shared changed timestamp,choice count or identifying fields. Only MUTUAL may show the current neutral private alias. A connection is separate from general friendship and from permission to send messages. No DM,contact exchange,public scoreboard,global dating notification or reward is added.

For this bounded local prototype,each account can keep at most one active private connection choice,and at most100active choice memberships exist globally. A first own like occupies only that account's choice,never the peer's slot. The peer may choose independently. Pending choice expiry is the source date's fixed24hour contact window,not the other participant's hidden like time. Both choices convert it to a private connection lasting at most30days. Source handles are opaque ended-date IDs already known to both participants. A REVOKED source never reopens;fresh consent requires a new date source. Unreviewed draft retention remains subject to independent human privacy/legal review.

Keeping a connection does not automatically requeue,accept a proposal,enter a date or restore chat after reconnect. MUTUAL exposes a short account/session/current-profile/negative-consent/source-bound return grant. Each participant explicitly joins a source-scoped120second return queue. The existing one-enrollment/account matcher must separate general and private-connection candidates and only pair two currently consenting members of the same MUTUAL source. They still individually accept a fresh proposal and separately enter the new timed DateRoom. Reuse the existing deadline/session/safety/receipt/quota/one-active-allocation engine;do not clone a second date-room allocator. No user may force or silently reserve the other's active match slot.

New sources are derived only from actual started-and-ended own DateRoom provenance within24hours. Historical Report provenance is not positive eligibility. Likes,private alias projection and return commands require current registered synthetic proof/profile/safety/bilateral-block checks. A passive private-connection peer check may not invent a session or trust a caller-supplied age/role;factor a narrow account/proof/profile owner port if needed. Return queue entries always bind each explicit participant's actual current authenticated session. A persisted connection is not renewed chat consent when a proof/session becomes valid again.

The audit found that current Matching.invalidate/block only traverse an active enrollment. Continuations outlive that enrollment,so profile save/withdraw/expiry,Social block and account erase need independent continuation invalidation ports even after a date ended. Revoke must remain authenticated/Origin/CSRF/key protected but independent of positive flag/key/proof/report availability and positive transport quota. Short grants and durable own negative-consent revisions defeat late likes/return commands;negative receipts describe original requests and cannot override later independent choices.

Lock order must change consistently before wiring return queues. Positive coordination shares the existing matcher SQL mutex,then captures every affected account and locks accounts in sorted order. Before any profile-expiry callback or proposal/date lock,it must capture and lock the union of active continuation headers related to every captured account in sorted header order. This union is bounded by100active memberships,and new positive header creation also requires the same mutex. This avoids an A-profile-expiry→A-header-set then B-profile-expiry→B-header-set cycle against a negative operation on a third participant.

Negative operations acquire neither the positive mutex nor new peer account locks. They lock their affected active continuation headers in sorted order,terminate source-linked proposals/dates,then delete active choice/queue memberships. Profile/Social/Identity wiring must invalidate continuations BEFORE the existing matcher callback;otherwise profile owns proposal→waits continuation while peer revoke owns continuation→waits proposal can deadlock. Ordinary Date Leave/last-socket interruption may end its current proposal without revoking the kept connection,but must never acquire a continuation header after taking proposal/date locks. Source guards used during proposal observation must honor that order and avoid introducing hidden new account locks.

Account deletion ends source-linked work before FK cascades. Active connection metadata must survive ordinary24hour date-history cleanup,so its minimal consent record cannot depend on a cascading date-history FK. Keep only the reviewed-in-code minimum:opaque source/pair,current profile snapshots and own choice/negative versions/times. No transcript or public identity copy. Own exports must omit partner IDs/fields and expose bounded own metadata only. Pending/active cleanup,24hour positive command receipts and90day negative fences/tombstones need bounded batches and actual tests;no deletion-from-backups or lawful-retention claim is made.

Acceptance includes actual simultaneous own likes and same-key retries;identical nonconsenting peer views after unilateral like;no general friendship/notification/progression;new private return queues never mix with general/another source;two independent fresh return choices/proposal accepts/date entries;one active allocation/account;revoke/block/profile/erase after enrollment is gone;late receipt waits;revoke-vs-like/return/block/profile races without deadlock or restoration;current proof/safety/session/IDOR limits;retention/export/erasure;native keyboard/mobile UI and held positive reply defeated by independent revoke. A schema or MUTUAL flag alone is not runtime completion. Actual commands/outcomes and retained failures belong to the evidence ledger.

The final adversarial handle test exposed different 404 messages for a foreign existing source and an unknown source. The continuation HTTP scope now normalizes DomainError 404 responses while preserving authentication,conflict,quota and service failures. Request IDs still vary per request;neither error reveals source existence. An exact committed return retry reads current matching state even after the short grant expired or Date Stop ended enrollment;it never renews enrollment or its deadline. A revoked source rejects that retry. Native observations expire after five seconds and held positive responses are discarded after independent withdrawal. These observations are bounded stale views,not instant delivery to every device.
