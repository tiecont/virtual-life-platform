# ADR0061 — Timed stage consent foundation

Historical foundation checkpoint at83fc369. The subsequent implemented runtime and verification are recorded in ADR0062 and m19-stage-checks.json;the foundation-only limits below describe this earlier checkpoint.

Status: foundation implemented and tested;M19-02 remains IN_PROGRESS. No Stage service/controller/UI is implemented or enabled by this checkpoint. M19-01's audience stage remains closed. This decision is not permission to provision real operators or publish a Lounge.

Audit:Events already supplies registered world-scoped organizer grants,per-event performer grants,current readiness,scoped moderator checks,account/event serialization and cancellation observation. Room already owns admission,seats and movement. Reuse those permissions and owners instead of granting role from a scene,client field or appearance. No real grant is provisioned here. Source references:events/permissions.ts,events/service.ts,rooms/service.ts and the M09 commit/unknown-receipt protocol.

The internal lifecycle is QUEUED → OFFERED → ACTIVE → ENDED. Host offer alone is not performance consent;the performer must explicitly accept. Queue wait is at most600seconds,offer at most120seconds and slot at most300seconds,with tighter trusted world/event/grant boundaries. Exact deadline wins over actions,clock rollback rejects,terminal receipts cannot reactivate,active accept/offer cannot renew a slot and closure chronology cannot predate an accepted start. These functions are trusted-clock models,not authorization or concurrent allocation proof.

Strict wire contracts require source/revision/version and explicit queue consent. They reject caller-selected actor,role,timestamps,duration or score. Trusted StagePolicy is separate from DTO imports to avoid World→Stage→Travel→Room→World cycles. It requires one performer,a bounded queue and a public listed Events venue with a solid stage. No existing world declares this policy yet;adding types does not offer Stage actions. Stage visibility is planned as anonymous slot presence with no peer identities,not shared profile disclosure.

Draft additive migration0030 stores event-owned consent revisions,stage slots and mutation receipts. Unique partial indexes permit one open request/account,one offer/room and one ACTIVE slot/room. Timestamp/phase constraints enforce bounded chronology. Event retention/account FKs cascade records;fair checked-order supports later bounded recovery. Storage tests use synthetic account/event/room references and direct SQL. They prove constraints and transactional rollback,not actual membership,permission,FIFO or API authorization. The migration has run only on disposable test databases;retained dev DB stays0029/stopped. Runtime cleanup of old stop receipts and current-source/grant recovery still need implementation.

The intended stage slot is a logical text/visual performance allocation. It does not teleport an avatar,claim a chair or force a room change. Preserve Room movement/identity ownership and the audience collision boundary;any later physical stage pose needs its own reviewed owner protocol. Starting a performance must be explicit and use current registered performer grants,listed event phase,current room/session/epoch,shared safety and bilateral block checks. Host offer and moderator revocation must use current trusted scope. UI must describe what actual authority is active and cannot infer it from a view or clothing.

Next implementation:room-owner source authorization wraps sorted account/event/slot SQL locks;serialize the per-room FIFO and cross-event occupancy before positive changes. Independent own Stop must increment a durable withdrawal revision and end own requests outside room/world while a start response is pending. Canonical retries and UI operation generations must prevent late responses/old keys from restoring consent. Observe deadlines after awaited guards. Event closure,grant/session/source loss,block,shutdown/restart and policy changes must end current authority without automatic restoration. Add bounded retention/export/erasure and sanitized route logging. No network/media/player work inside transactions.

M19-02 is not VERIFIED until real endpoints,grant/source/IDOR/role/time/race/receipt rollback/expiry/restart tests and native host/performer controls pass. Required future tests include multiple contenders for one actual room slot,ordinary/foreign/expired grants denied,host offer cannot force ACTIVE,Stop versus blocked/committed start with lost reply,actual moderator revocation and canonical old retries,private metadata/export/erasure and desktop/mobile journeys. M19-03..06 remain separate. Keep real flags OFF and B-001/B-002/B-003 unchanged.
