# ADR 0009 - Enforce the single room owner deployment

Status: Accepted local implementation, 2026-11-02 (M06-07).

The measured baseline does not justify distributing room ownership. Keep one authoritative in-memory room process per platform database schema. An accidental second process must fail room admission rather than create independent memberships for the same accounts.

RoomAuthority lazily acquires PostgreSQL session advisory lock `(1447840561, hashtext(current_schema()))` on a dedicated pool connection. A schema hash collision can deny availability but cannot grant two owners the same key. Separate test schemas are independent platforms. All room commands, including aggregate room listing and connection snapshots, verify the held lock before and after work. Viewer delta fanout verifies again immediately before publishing. SDK membership permission also checks authority. A one-second heartbeat checks idle ownership; individual queries time out after one second and pool acquisition after two seconds. Close destroys the dedicated connection instead of returning a session lock to the pool.

If another owner holds the lock, room commands return WORLD_UNAVAILABLE and readiness returns 503 after that attempt. No lock is acquired just to answer health requests or identity/social operations. A blocked process may retry on a subsequent room command after the owner stops. Connection error/end, missing lock or deadline changes a previously held owner irreversibly to lost: discard ephemeral memberships/seats/receipts, emit room.ended(authority-lost), disconnect room sockets and reject subsequent room work. Restart is required; a lost process never silently reacquires authority. The additive prerelease v1 ended reason is accepted by contracts and the SDK; no deployed legacy client is upgraded here.

This is a single-instance deployment guard, not a distributed fencing protocol. It assumes one PostgreSQL primary and direct/session-affine connections, not PgBouncer transaction pooling. Do not promote independent database primaries or deploy multiple room replicas using this lock as a failover system. A stopped or partitioned process may retain stale local memory until it runs/checks again; clients require epoch/membership checks and snapshot recovery. There is no durable engine write protected by a monotonic fencing token in this slice. Future persistent engine consumers must enforce their own transactions and the future ownership protocol before distributed failover is enabled. A tiny check-to-output race on an unreliable network is not certified as linearizable delivery; old epochs must always be rejected by consumers.

Tests use real child processes and disposable PostgreSQL: competing live admission denies the second owner; pause the first with SIGSTOP, terminate only its test lock backend, admit the second, resume the first, observe authority-lost and reject further mutations even after the replacement stops. A slow in-flight admission cannot publish a delta or acknowledge success after its lock connection is terminated. Graceful SIGTERM and SIGKILL restart on the same port preserve identity and reset ephemeral room state truthfully. Fake timers verify query/acquisition deadlines and destruction of late connections. This is not a WAN partition, multi-primary or distributed lease test.

Rollback: drain/stop the current owner before starting another, keep one API replica, require fresh client snapshots. No schema migration, Redis adapter, production failover, infrastructure change or public release. Future lease, routing, monotonic fencing and partition tests remain in FUTURE-OWNERSHIP.md.
