# ADR0086 — Explicit Deadline session association

Status: accepted and locally verified for M15-02,from4c5e2ee. Actual commands and initial failures are retained in [the verification ledger](https://github.com/tiecont/virtual-life-platform/blob/cef7dc17172f7c6cda930c99648a5e3ad609cc55/docs/agent/evidence/m15-identity-checks.json);public federation and whole-world integration remain separate.

City remains the account/session authority. An authenticated city user explicitly associates the existing HttpOnly Deadline guest cookie from this browser. The local-only adapter calls the selected Deadline baseline's actual `GET /api/v1/me`,forwarding only that cookie to a fixed exact loopback origin. It accepts no caller-supplied guest/account ID,name or avatar as ownership proof. It follows no redirects and bounds response size,time and concurrent work. This is a possession-proven association of two existing sessions,not a new login provider or a claim of production cross-domain federation.

The city write requires its own current signed session,Origin,CSRF and idempotency key. Source proof is rechecked after acquiring city account/subject serialization;current city authority is checked before commit. Unique provider/subject and provider/account constraints prevent two city accounts silently claiming one Deadline identity. Another guest is not silently merged into an existing association. Registered upgrades/rotation retain the city account ID and mapping. Original Deadline token/profile/history/data remain untouched;no history import or legacy schema rewrite is included. No source token or CSRF is stored,exported or logged.

An additive city-owned link row records private consent/revision,not live source authentication or public presence. Linking grants no world,staff,moderator or adult eligibility privilege. A historical association can remain after a source session expires;every new positive association still requires current source proof. Export is owner-only;city erasure cascades link/receipt rows without deleting the independent legacy account.

Positive requests use expected revisions,durable fingerprints/receipts and a persistent rolling24-command/day counter. Receipts are bounded100peraccount and30days with sequence-based pruning;the rate counter cannot be reset by unlinking or pruning receipts. Exact old retries return current state and cannot reactivate consent. Unlink has an independent negative lane,needs no legacy cookie/provider availability,and advances a revision barrier even when no prior link exists. It can beat one positive command issued from the same observed revision;staler withdrawal frames must refresh. The native panel discards late positive replies after withdrawal or session change.

Default configuration is OFF and production rejects local activation. Only explicit127.0.0.1 HTTP origins with a port/no credentials/path/query/fragment are accepted. Same-host local cookie compatibility is the authorized offline scope;public federation remains a separate operator/release design. Module02 verifies identity association from Portal controls;playable room/focus/scene integration follows M15-03..04 and is not claimed here.

Acceptance must use the exact pinned legacy API in its own disposable database/process,alongside city HTTP/DB and browser controls. Verify name collisions,concurrent ownership/retries,upgrade/rotation,revocation/expiry,SQL-wait rechecks,rollback,negative consent/outages,bounds and own export/erasure. Never connect the original legacy server or database. Keep the archive baseline immutable and all real rollout flags OFF.
