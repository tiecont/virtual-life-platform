# ADR0067 — Isolated encrypted profile with bounded write authority

M20-02 adds only an own private introduction profile. No matchmaking,private Room,date chat,mutual continuation,public provider or real participant operation is introduced. M20-01's approvals remain literally false and M20-07 remains BLOCKED_EXTERNAL. The actual positive service requires NODE_ENV=test,explicit LOCAL_DATING_PROTOTYPE=1,a dedicated key and a trusted current synthetic eligibility port. Normal development/production users have no positive eligibility provider. The optional built-in DATING_TEST_PROOFS reader additionally requires a disposable loopback virtual_city_test database;production local activation is rejected. A test fixture row is not real-world age verification.

Identity owns authentication/registered status;the new restricted.dating owner owns separate profile state/receipts. Synthetic proof metadata has a separate test-fixture table/owner,contains only account/times/revocation and has no issuance HTTP endpoint. Proof source/account/minimumAge/policy/time/expiry/revocation are checked from trusted server data on positive reads/saves;client age/roles/proof or peer IDs are rejected. Shared current sanctions/incident policy also apply. No Dating world is installed and no Room capacity is allocated. Existing generic directory/admission/private-reporting gaps from ADR0066 still must be closed before installing date rooms.

Private choices are finite safe aliases,one-to-three unique interests and preferred topics,and calm/lively/either pace. No demographics,location,birthdate,biography,photos,URLs or free text are required. Mutual matching of those preferences remains M20-03,not a claimed profile feature. Choosing a city nickname/avatar or changing global privacy never copies fields into this profile. There are no global profile/presence/discovery/notification/analytics updates and no dating payload is emitted on the shared socket. The own authenticated export may explicitly include the owner's private choices;it is not a public profile projection.

AES-256-GCM uses a separate DATING_PROFILE_KEY/key ID and random12byte IV. AAD binds domain version,key ID,account and profile revision. SQL stores no plaintext alias/preferences;mutation fingerprints are purpose-HMACs,not unkeyed sensitive-value hashes. Wrong key/AAD/tampering fails closed and never returns partial plaintext. Missing/wrong keys do not prevent authenticated withdrawal or account erasure. Own export reports data unavailable rather than claiming it was erased. There is no automatic key rotation/re-encryption or production key provisioning in this slice;synthetic browser keys exist only in test tooling.

The transaction order is account lock→current session/proof→profile/receipt rows. It is an own-account flow only. Future relational matching must capture peers before sorted account locking and revalidate the target set;never attach a callback that acquires a new lower account lock after this lock. Every positive mutation requires a<=30second purpose-HMAC write grant bound to account/session/current revision and clipped by proof/session/profile expiry. The client keeps it in memory/body only. Exact-key retries return canonical current state after fresh authorization,never the old private payload. Twenty successful saves/account/hour is durable across restarts. Invalid grants/versions and post-await expiry roll back profile+receipt atomically.

Withdrawal needs only the current authenticated session,strict Origin/CSRF/key/body;it ignores positive install/key/proof/admission state. It erases the encrypted blob and increments the consent revision,so a positive grant issued before withdrawal cannot restore it. Same-key negative retries confirm their original withdrawal rather than revoking a later explicit new choice. UI therefore says withdrawal was recorded and asks for a fresh observation of current state. A new withdrawal uses a new key. At most200negative receipts/account/day are stored;above that bound negative consent still commits without another receipt. Such overflow retries may advance the fence again and only strengthen withdrawal. There is no reward/contact/duplicate profile effect. A stale positive grant expires in30seconds even if old receipts/tombstones have been purged.

Profile inactivity is measured from the last explicit save,not passive reads. At30days,cleanup clears encrypted choices and advances to an inactive90day negative-consent tombstone;expired inactive rows may then be removed. Save receipts keep24hours;negative receipts keep90days. Synthetic eligibility rows are purged after expiry,which is bounded to24hours from verification. Fair expiry-ordered100row batches/table run on the existing3second service loop;backlogs need additional batches. Shutdown waits for maintenance. All durations remain unreviewed local defaults,not legally approved retention. Account FK cascades remove profile/receipt/test-proof state. No dating data is a public metric or a moderation finding.

The private form is gated server-side before rendering and has no global navigation/discovery card. Fields load only after current identity/session and synthetic eligibility checks;all choices clear on hidden/offline/socket loss/revocation/observation expiry. Native controls use explicit save consent,original-key uncertain retry and independent withdrawal during a pending save. A separate authenticated private withdrawal page works after eligibility loss. No data/grant is stored in localStorage/URLs. Responses are no-store;the web path has no-referrer/noindex and existing media/capture denial. The API structured request logger redacts the whole private prefix,not only IDs. This is the implemented logger scope;future upstream traces/access logs need equivalent review before any real pilot.

Migration0033 is additive and preserves all prior checksums. Rollback disables/removes positive private prototype configuration and leaves independent withdrawal/export/erasure/migrations available;do not downgrade or destroy existing data. Actual commands/results and limits are recorded in m20-profile-checks.json. Passing synthetic API/browser tests cannot approve a real verification process,operated dating service or legal/privacy signoff.
