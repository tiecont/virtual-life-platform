# ADR0063 — Original virtual mocktails on shared Hospitality

M19-03 uses the existing Hospitality engine without a second order/shift store. Lounge world1.2.0 offers policy1.0.0 with two original virtual menu entries, Moonlit mint-lime and Berry spark. Both use one timed-course workflow with a server-owned two-second preparation deadline. The original scene1.0.0 and its solid stage/counter boundaries stay unchanged. Menu configuration changes the Lounge source fingerprint; no media or external artwork is added. Existing Events version pins remain enforced when the world version changes.

Bartending is a voluntary simulation role. A participant explicitly starts a current-room shift with the existing consent revision. The world offers only bartender actions claim/prepare/ready/serve; a client cannot invent cook/server permissions, a stage role or a moderator grant. There are at most two bartenders, at most two active assignments per bartender and ten open room orders. Shifts still use Hospitality's existing four-hour maximum, own independent Stop, role/source/session/safety checks and disconnect recovery. This decision provisions no real staff and grants no trusted operator authority.

A seated current customer chooses an allowed virtual item. Ordinary unshifted participants cannot claim it. Assigned current bartenders prepare, wait until the server deadline, mark ready and serve once. Only the customer acknowledges the served order. Existing SQL course uniqueness, completion/outbox transaction and mutation receipts apply; retries do not add drinks, completion effects or rewards. Default progression remains disabled. No payment, alcohol, tip, custom score, real inventory or external vendor field is accepted. The item names describe fictional virtual choices rather than a real recipe or transaction.

Consent stays with both participants. Bartender refusal requeues unfinished work and privately excludes that bartender from the same order. A bilateral block closes service contact through the existing transaction hook. A customer may withdraw unfinished service outside the original room/world, and a withdrawn placement receipt remains terminal. Staff Stop can return an already committed assignment while its HTTP response is still pending. Leaving the customer's original seat/session/visit can cancel unfinished service; no automatic reactivation is introduced.

The Restaurant audit found reusable transport/receipt/observation behavior inside world-specific native components. Extract `VoluntaryStaffControls` and `useHospitalityOrders` into app/components, parameterized by world and trusted policy. Restaurant keeps its own policy, exact work controls and multi-course kitchen-pass view. Lounge supplies a separate one-course mocktail view. Neither world imports the other's implementation or database. The hook preserves existing eight-second request deadlines, same-key uncertain retries, ten-second queue observations, thirty-second menu/private history and independent negative actions. A view or cached shift is never server authority.

No new migration, engine fork, role-provisioning endpoint, general chat/reaction feed, media player, new report category or reward consumer is needed. Current native Room safety remains available; dedicated Lounge reports/emergency/load acceptance is M19-06. The local install and registry gates remain OFF by default, and production rejects the local option. This is not a real bar, media clearance or public/operator approval. Verification and any remaining implementation work are recorded in m19-mocktail-checks.json and the latest agent checkpoint.
