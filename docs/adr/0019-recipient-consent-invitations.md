# ADR0019 - Recipient consent and confidential invitation refresh

Status: local M09-03 implementation; verification is recorded separately in agent evidence.

Invitations are a separate consent state machine, not friendship requests or travel capabilities. Recipients opt in explicitly (default false), and both parties must currently be friends without a block in either direction. Trusted social ports check relationships using the caller transaction. A social withdrawal hook cancels pending invitations inside the same pair-locked transaction as block/unfriend; errors roll back both domains. Re-friending or re-enabling preferences never restores a cancelled pending invitation.

Only currently available, listed public worlds can be invited to. Destination contains versioned world/scene, no room, sender location, private presence, arbitrary message or redirect. Private/hidden/restricted worlds including dating are rejected even for reviewed adults. This conservative scope avoids revealing private visits through invitations; expanding it requires a distinct contextual consent design. Sending an invitation proposes a public destination and does not assert that its sender is there.

Invitations expire after2min. They persist PENDING/ACCEPTED/DECLINED/CANCELLED/EXPIRED, account-scoped idempotency fingerprints, a unique pending directional pair, six creations/minute and20/hour, plus50 pending incoming capacity. These are local engineering defaults. Accepted is a historical consent outcome: no room reservations, travel token, READY state or teleport. M09-04 will need a new fresh scoped intent using the recipient's own source, session and current policy.

All create/respond/preference mutations use identity account advisory locks, fresh sessions, strict schemas, Origin/CSRF and UUID keys. Registry authorization runs before taking account locks because it uses a separate pool; a synchronous public-disclosure check runs again inside the transaction. This prevents saturating the pool with lock-waiting requests that depend on another free connection. Registry/safety access is an observation here, not admission authority; actual travel must reauthorize at its switch. Lists use a fresh actor catalog before the transaction, filter again for current public availability and current relationships inside, and never infer someone else's presence.

Account-scoped invitation.received/responded socket hints contain only schemaVersion1. No actor/world/room/receipt IDs or counts are broadcast. Reconnect refreshes the inbox; notification delivery is best-effort. After a delayed hint, the authoritative list can truthfully return nothing because current block/consent/flags changed. Client clears projections on disconnect, identity replacement and relationship refresh, retains mutation keys after uncertain network failure, ignores stale refreshes and refreshes at pending deadlines.

Migration0009 adds invitation-owned preferences, invitations and mutation receipts. Own export includes at most100 body-free historical receipts and destination with explicit truncation, omitting peer account IDs/profiles and secrets. Account deletion cascades. Bounded maintenance expires pending rows and purges terminal metadata after24h; local retention defaults still require human policy approval. Roll back by closing invitation entry points, retaining additive tables and receipt metadata; no automatic destructive down migration. No remote operation, staff grant, world flag or public activation follows from this code.
