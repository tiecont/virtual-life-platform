# ADR 0057 — Policy-bound voluntary hospitality roles

Status: accepted for local implementation. Actual verification is recorded in m18-roles-checks.json when collected. No release approval.

Audit: M11 already owns voluntary shifts, account/room authorization, four-hour expiry, receipts, bounded recovery, assigned work requeue and private export. There is no persisted Server/Cook distinction: a generic staff predicate currently permits all service actions. Restaurant perspective radios from M18-01 are presentation only. The existing appearance owner requires separate entitlements and uniform policy; Restaurant keeps aprons forbidden and grants no new cosmetic authority.

Use an optional trusted staffing.roles policy with unique keys/labels and explicit action allowlists. Migration0027 adds role_key to existing shifts, defaulting to staff, and an account consent revision. Restaurant world1.1.0/scene1.0.0 offers Server(claim,serve) and Cook(claim,prepare,ready), at most2voluntary workers per actual room. Clients request an offered role, never submit an allowlist. New role worlds require expectedRevision on start/switch. No role entitlement, moderator permission, external staff provisioning, rewards or romantic obligation is introduced. Existing generic worlds retain their input/output shapes and policy behavior; extra role fields there still fail422. The optional test/provisioning staff port cannot override role-world action allowlists.

Start retains one open shift/account. Switch requires the same current authenticated room/epoch/membership, policy version and active shift. It locks account/customer participants through existing room/event ownership, requeues unfinished assigned work and clears preparation deadlines in the same SQL transaction, updates the role, advances revision and stores a fingerprint receipt. Served courses remain retained by the existing requeue implementation. The original shift ID/start/expiry are unchanged. Exact retries return canonical current state, not the earlier role, and cannot reacquire work. Receipt failure rolls back role, revision and requeue together. Wrong-role and off-shift commands fail before state transitions.

Independent POST staff/stop requires authentication/Origin/CSRF, not a room/catalog/shift ID. It serializes with pending starts/switches, increments revision, ends own work and requeues outstanding assignments. Repeated stop is semantically idempotent but may advance revision. If stop wins first, stale role input cannot start work; if start wins first, stop ends it. Traditional end also invalidates role consent. Recovery ending a role shift advances revision, so stale input cannot silently renew it after disconnect/expiry/restart. Recovery/retention/session/safety/block behavior continues through the shared engine. Stop uses existing HTTP/session limits and bounded database deadlines.

The original expiry implementation sampled the clock twice: a real advancing clock could create expires_at greater than started_at+4hours and violate SQL. Derive both endpoints from one trusted timestamp; a deterministic clock advancing on every read covers this. No client-supplied time/duration or weaker SQL constraint is accepted.

GET staff/state supplies private canonical shift+revision. The native work UI separates role selection from an explicit start/switch button, uses exact-key uncertain retries,30second observations,8second network deadlines and identity/visit/hidden/offline cleanup. Independent stop aborts a stale UI write and remains available during pending responses or failed status reads; revision ordering supplies the actual server guarantee. Perspective radios still issue no mutation. Existing own-shift endpoints remain compatible for generic staff; role-bearing output is an additive prerelease schema change and older strict readers must upgrade before using role worlds.

This slice enables staffing and tests role enforcement against real orders, but offers no Restaurant menu or customer order UI. Cook/server handoff, multi-course loop and coordination interaction remain M18-04. Current assignment owner restrictions remain enforced; no full two-person service-completion claim follows from policy roles alone. Restaurant private table/dinner consent/report acceptance and final load/mobile acceptance remain M18-05/06.

History/export includes own role without membership/session proof. Account erasure cascades shift/receipt/revision records; existing90day shift retention applies. No identity, DB or room owner is duplicated. Disable the local world for rollback and retain additive migration/history. Dropping columns/table or narrowing operation constraints can destroy history/reject receipts and needs a reviewed backup/data decision; no destructive rollback or production/legacy/remote action is performed. Real rollout flags remain off and local production activation remains rejected.
