# ADR0035: Durable private event catalog and RSVP allocation

Status: Accepted local implementation, verification recorded separately. Date: 2026-11-03.

M12-02 implements scheduled silent activities and one-place-per-account RSVPs. WorldDefinition already advertised events capability without an implementation; no existing definition used it. The capability now requires an explicit versioned eventPolicy within world capacity. No existing legacy route is replaced. A guarded registry callback captures generation before awaited authorization and supplies a final validity check, preventing disable/re-enable during an outstanding event transaction from admitting stale work.

EventService.schedule is an internal server adapter port, not an HTTP route. It authenticates and rechecks a trusted organizer permission inside the transaction; the default app provides no organizer grants. Only silent audience is accepted; interactive/live-audience requests reject until M12-04 introduces reviewed moderator approval. Schedule creation checks policy/world versions, PostgreSQL timezone availability, UTC ordering and future opensAt within thirty days. Capacity cannot exceed the declared world policy. There are at most100 nonterminal schedules/world, twelve new schedules/hour/organizer and thirty new mutation receipts/minute/account. Scheduling is serialized per schema/world; own exact-key retries reuse the durable event. Metadata titles are trusted reviewed adapter input, not public free text.

Authenticated GET events requires a worldSlug and returns at most50 upcoming listed event projections plus truncation. GET events/:id returns current own RSVP without an attendee list, organizer identity or other account IDs. At this slice, restricted/private/hidden worlds including dating are closed, even with hypothetical access proof. Private events are owner-only; participant invitations/access expansion belong to M12-05. Current world enablement/version/policy, shared sanctions/incident controls and bilateral organizer block are checked. The organizer and participant account locks serialize contact/sanction/deletion changes; safety is reread using the same DB transaction. Request logging redacts IDs and queries.

POST events/:id/rsvp uses strict schemaVersion-only input with Origin/CSRF/key. It takes sorted participant/organizer account locks then the event row FOR UPDATE, observes trusted phase, reads confirmed allocations under that same lock and inserts/updates the unique event/account row with its receipt. It admits only before startsAt, rechecks the deadline and generation before returning to COMMIT, and charges one place. Another world or caller cannot supply authority, timestamps or attendee identity. At most ten future active RSVPs/account and twelve new join commands/hour are allowed; exact retries bypass durable command budgets and return canonical state. All event allocation writers must use this domain-owned lock; pure counts without the lock would not suffice. No production throughput or multi-replica runtime claim is made.

Own withdraw works even when the origin is disabled/blocked and returns only own participation metadata. It releases capacity and atomically stores its receipt; an old RSVP key observes CANCELLED rather than resurrecting it. A new explicit request may rejoin if policy permits. Block cancels organizer/participant RSVPs inside the existing social transaction, with callback failure rolling back both actions. Unfriend alone does not withdraw. Per-event uniqueness and actual twenty-account/two-place TCP tests verify allocation; receipt-failure tests verify rollback. Erasure cascades participant allocations, and counting rows under the event lock means no stale capacity counter survives deletion. Organizer deletion cascades the schedule; cancellation notices are M12-04.

Calendar download is an explicit POST with optIn:true for a current confirmed participant. GET has no calendar route; neither RSVP nor reading schedules emits email, invitations or files. The generated attachment uses UTC DTSTART/DTEND at calendar second precision, explicit IANA zone/offset labels, stable creation DTSTAMP/UID, escaped text and UTF-8 octet folding. No attendee/organizer contact, transport secret, external URL or tracking identifier is embedded. It does not grant room admission or register an external calendar. Actual event UI/discovery remains later module work; timezone labels are verified in the API projection and attachment.

Every relevant read/write reconciles trusted event phase. Main maintenance fairly observes twenty active schedules/batch every three seconds; natural end expires outstanding RSVPs once without attendance/reward. Restart reads persisted schedules without inventing live room membership. Terminal records/receipts retain at most ninety days with100-event bounded purge; own export projects elapsed states and is bounded100 per collection. Scheduling delays/DB outages are not a realtime notification SLA. No event-started broadcast, organizer cancellation endpoint, table holds/check-in/waitlist or external calendar delivery is claimed yet.

Migration0019 adds events, unique RSVPs, durable mutation receipts and recovery ordering with account/event cascades and strict SQL time/phase constraints. Rollback disables event adapters/policies while retaining tables/data, with no destructive down migration or legacy DB writes. M12-03 must integrate holds/party/resource allocation under an equally authoritative lock and recheck actual room admission. M12-04/05 own roles, moderator audience approval, cancellation notices and expanded privacy-filtered discovery. All real rollout flags remain OFF. See m12-rsvp-checks.json for actual commands, initial failures and limits.
