# ADR0032: Transactional order completion and progress outbox

Status: Accepted local implementation. Date:2026-11-03.

Only the customer acknowledges a fully SERVED order. Staff cannot unilaterally complete it or select rewards. POST orders/:id/complete uses strict schemaVersion/expectedVersion,authenticated own account,Origin/CSRF/key. It requires a validated workflow and every served course ledger entry. Own acknowledgment remains possible after leaving/world closure because it observes completed service rather than contacting another participant. M11-06 owns future safety/refusal policy;M13 owns actual progression grants.

Account and order locks serialize completion with retries,deletion and competing updates. One transaction updates COMPLETED/version,writes a unique order completion,creates its outbox event and persists its mutation receipt. Any insert failure rolls back all four effects. Exact retries return canonical private state;different input under an old key conflicts;other new keys on a terminal completion do not create more receipts or outcomes. Eight actual TCP retries and restart replay verify one completion/outbox. No automatic tick completion exists.

The internal OrderCompleted event contains scoped IDs/world/item/version/coursecount/completedAt needed by trusted consumers. It is not published to sockets,HTTP,exports or logs. No generic event or reward submission route exists. Outbox stores only event linkage and monotonic ordering;payload derives from the durable order/completion. Participant erasure or terminal order retention cascades pending events,delivery/retry metadata. Future consumers must implement their own export/erasure ownership;sample SQL consumers are synthetic verification only.

Trusted registered completion sinks are bounded8,each with a stable unique versioned consumer key. Dispatch batches20events/consumer,locks both participant accounts and outbox row,rechecks a unique delivery receipt,executes the hook's SQL and stores delivery in the same transaction. Hook/receipt failure rolls back all DB business effects. A separate sanitized retry record uses bounded exponential delay1..60seconds;one failed consumer does not prevent another consumer from handling the event. No raw error/body is retained. Restart resumes pending receipts;competing dispatchers do not double-apply a committed effect. main.ts schedules dispatch with hospitality maintenance;close awaits in-flight dispatch.

Exactly-once applies to committed business effects inside this PostgreSQL transaction,not arbitrary external delivery. Hooks are trusted in-process code and must await only the supplied transaction's DB queries,no network or detached tasks/transaction control. SQL statement/lock deadlines apply;noncooperative JS hooks remain an operational review gate and no arbitrary/plugin caller can register one. Default app registers zero consumers,so it stores pending events but grants no progression/currency. Future M13 must register reviewed transactional handlers;changing consumer keys represents a new subscription and needs reconciliation review.

Migration0017 adds unique completions,outbox,delivery and retry tables plus complete operation. Rollback disables relevant adapters/consumers and preserves data;never drop retained orders or mutate legacy DBs. Events share the bounded90day terminal retention window;this is not an infinite reliable event archive or production delivery SLA. Evidence m11-completion-checks.json records actual concurrency,rollback,retry/restart,batch/privacy/deletion verification. No rollout flag,legacy copy or public release occurred.
