# ADR0062 — Durable logical stage and independent Stop

M19-02 extends the tested foundation in ADR0061 with an Events-owned service, strict HTTP routes and native Lounge controls. This is a logical text/visual allocation. Room retains movement, membership, chairs and the solid audience stage boundary. No audio, video, stream, user upload or forced movement is introduced. Lounge world1.1.0 declares stage policy1.0.0: one performer, ten open requests including any offered/active slot, thirty-second offers, sixty-second slots and at most ten minutes waiting. The scene stays1.0.0. Existing world1.0.0 event records cannot silently inherit new authority; current Events version checks continue to apply. Real installation/registry flags stay OFF and production still rejects the local option.

Only a registered account with a current persisted event-specific performer grant can queue or accept. A current registered organizer of that event or a scoped moderator may offer the FIFO head. An offer never starts a performance. Explicit acceptance requires the original connected visit, current consent revision and expected version. A moderator/host may revoke outside the room; own withdrawal and Stop remain available outside admission and world availability. There is no self-provisioning or client-selected role. Test grants exist only in disposable databases.

Positive operations enter Room's serialized source owner before sorted account locks, the Events row and Stage rows. Captured participant references are checked again after locking; changed references return a retryable unavailable result instead of acquiring accounts out of order. All open room rows participate in FIFO/capacity checks, including requests for other events. Another event cannot bypass an older room request; it must wait for withdrawal or expiry. Unique partial SQL indexes remain the last allocation fence. The one-instance room authority is still required; this does not add multi-instance room ownership.

Current event/world policy, attached registered sessions, performer and offering-host grants, shared safety and bilateral blocks are rechecked. Durations are server-owned and clipped by event, original connected-session and grant authority. Renewal or retry cannot extend an existing deadline. A real SQL receipt wait test exposed acceptance committing after its offer deadline; the final acceptance fence now checks the original offer deadline after the receipt INSERT as well as the slot/authority deadline. Failure rolls back state and receipt together.

Stop uses an independent account transaction, increments a durable consent revision and ends all own open slots atomically with its receipt. Sorted account locks serialize a pending start against Stop. A late request with an old revision fails; a committed old mutation key returns terminal canonical state after withdrawal. The UI invalidates prior operation generations before Stop, keeps Stop enabled during a pending positive request and discards late start replies. Uncertain retries reuse the original key and payload. Request deadlines are eight seconds; stage observations expire after five seconds, own history without a current stage after thirty seconds. Hidden/offline/source/identity changes invalidate visible authority. Refresh does not imply a new consent or performance.

Events observation closes slots in the event cancellation/end transaction and includes Stage participants in cancellation notices. Bilateral block closes relevant organizer/host contact in the block transaction; unfriend alone does not revoke a performance grant. These callbacks never enqueue Room work while holding account locks. Fair maintenance checks twenty rows per batch, advances a SQL recovery sequence even for healthy rows, and ends authority lost through grant/session/source/restart/safety/world changes. A last-socket disconnect ends stage participation at the next observation, without hospitality's reconnect grace. No automatic restoration occurs. The main service scheduler runs every three seconds; large backlogs require multiple bounded batches, so this is not a zero-latency revocation claim. Every positive action separately revalidates authority.

Views expose anonymous occupancy, own slots and opaque queue slots only to current scoped operators. No peer account/profile, offering-host ID, room/session/membership proof or mutation fingerprint is exposed by Stage DTOs. Own export is bounded to100 rows. Account/event deletion cascades own records; the deletion owner also ends work offered by a deleted moderator and clears its host-source proof. Parent Events ninety-day retention cascades slots and linked receipts. Up to100 unlinked Stop receipts older than ninety days are removed per maintenance batch; the current withdrawal revision is retained until account erasure. New nested slot IDs and query values are redacted from request logs.

Migration0030 is additive and its committed checksum is unchanged. Rollback disables the Lounge world/installation and leaves durable history available for own withdrawal/export. No destructive downgrade is required. M19-03 mocktail service, M19-04 audience feed/RSVP, M19-05 media clearance and M19-06 load/emergency acceptance remain separate tasks. Stage permission/control tests do not establish an operated public Lounge, real operator coverage, a performance content feed or cleared media rights. Verification and any remaining gates are recorded in m19-stage-checks.json.
