# ADR 0058 — Course-match kitchen pass on the shared service ledger

Status: implemented locally; actual verification is recorded in m18-courses-checks.json when collected. Public rollout remains off.

Audit: existing Hospitality workflows already snapshot1..5courses/order, enforce trusted preparation deadlines, serialize expected versions, uniquely record each served course and atomically create customer completion/outbox/receipt. Restaurant roles from03 intentionally cannot complete a shared Cook/Server order without a handoff. Add a narrow optional workflow rule rather than relaxing generic assignment checks or creating another gameplay database.

Restaurant world1.2.0/scene1.0.0/servicepolicy1.1.0 offers one original virtual dinner with starter/main/dessert and two-second server preparation per course. A workflow snapshots optional handoff `{kind:course-match,fromRole:cook,toRole:server}`; policy validation requires offered preparation/service role capabilities. Existing workflows without handoff preserve their transitions. Server's existing claim privilege remains for compatibility, but the intended kitchen journey uses a Cook ticket; a Server holding an unprepared ticket can explicitly refuse/requeue or change role,never prepare under Server privileges.

The coordination interaction is cooperative course matching,not a reaction-speed score. Cook claims,prepares and calls a course ready. Server sees the anonymous current ticket/call,chooses the matching course from the workflow choices and explicitly takes the plate. Wrong choices change nothing. POST orders/:id/pick-up accepts only current source,expectedVersion and courseKey;not score,time,recipe,assignee or privilege input. It authenticates the Server,checks exact frozen workflow/current policy roles,original seated customer,active Cook visit/session/safety/shift,three bilateral contact relationships,deadline and queue cap. Sorted diner/Cook/Server account locks precede row mutation. Transfer+version+fingerprint receipt commit together;rollback restores Cook ownership. A concurrent exact-key retry has one effect. Distinct stale handoff attempts conflict. Pickup neither serves a course nor grants progress.

The receiving Server alone serves the plate through the existing assigned-owner service action. Intermediate courses return to PENDING/unassigned while retaining served-course ledger and next course index;the Cook must take the next ticket voluntarily. Final service retains the Server assignment and waits for the customer's separate acknowledgment. Completion continues through the existing unique SQL completion+outbox transaction. This is two service workers plus one diner,not two total browser identities. No automatic reward sink or credit for the Cook is added;default completion sinks remain unchanged. Client state never declares a course served or a timer elapsed.

Actual browser QA caught client request amplification:reloading menu/history/staff/queue after every Cook action exceeded the existing60requests/session/minute guard. Keep that guard. Merge confirmed customer mutation results into known bounded own history and refresh only the worker's queue after confirmed service actions. These updates never extend menu/history observation TTL;failed/uncertain actions still reconcile through the full canonical read. A slow response also rechecks current visibility/online state. Final browser proof records worker request counts and rate-limit outcomes;no synthetic increase to request budgets is used.

Ownership is withdrawn on requeue/handoff. A former worker's retry can therefore fail404 after another actor takes responsibility;it cannot restore an assignment or duplicate a served course. Exact pickup retries while the receiver remains authorized observe canonical state. An uncertain intermediate serve may refresh into the next kitchen ticket;the customer-owned history is canonical. Completion retries remain idempotent after final service. Existing refusal,customer withdrawal,block,role-change/stop,disconnect recovery,clock checks,session/safety,retention/export/erasure and restart behavior continue through owners. Queue projection additionally filters blocked Cook/Server relationships. No peer account IDs/roster are exposed in service tickets.

GET orders/mine returns at most20own orders with truncation,independently of room membership;existing permission checks protect another account's order. The shared shell adds an advisory seated boolean to its child slot;server seat proof remains authoritative. Native menu/order/queue/game controls use strict schemas,8second network deadlines,exact-key uncertain retries,30second menu/history and10second queue observations,source/identity/hidden/offline cleanup. Withdraw unfinished service can abort a pending UI write;the server version/transaction determines the legitimate race outcome. Ready time is displayed from server timestamps. Manual refresh after the other worker's step avoids fabricated realtime claims. No canvas-only or timed dexterity requirement is imposed.

Migration0028 only expands existing mutation operation constraints for pick-up;course and completion persistence are reused. Optional passChoices is an additive prerelease order projection;older strict readers must upgrade for handoff workflows. World/service version changes intentionally invalidate stale runtime policy inputs. No historical order recipe is rewritten. Disable the local Restaurant module/flag for rollback and retain0028 data;removing the operation constraint while pickup receipts remain would be incompatible and requires review. No destructive rollback,legacy copy,real-world food sale,media/operator grant,remote write or release action is performed. Dinner/private-table consent and full world acceptance remain M18-05/06.
