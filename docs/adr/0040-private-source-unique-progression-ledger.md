# ADR0040: Private source-unique progression ledger

Status: Local implementation; verification in m13-ledger-checks.json. Date:2026-11-03.

Progression accepts no public raw reward event or amount. The authenticated claim-focus endpoint accepts only an own focus ID. FocusService's completion port locks/reconciles the account-owned timer and passes canonical account/source/world/completion time inside the same SQL transaction. Unfinished/cancelled/foreign timers cannot authorize XP. Reward minting and any transition from elapsed active timer to completed roll back together on grant failure. Exact retry keys are unnecessary for a claim whose entire authority is an immutable source identity; the unique account/kind/source constraint makes all identical claims idempotent. HTTP Origin/CSRF/session bounds and strict bodies still apply.

The reviewed hospitality sink uses the existing durable transactional outbox. It derives customer/staff observations from the validated completed order and applies one private grant for each participant, with the other as a partner. The outbox already holds both account locks in canonical order; the ledger reuses the same account advisory lock key. Default progression remains disabled and registers no sink. Explicit trusted app options may enable the validated policy for local fixtures. No new public world flag or staff permission follows from enabling progression.

Under each account lock, the service rechecks source uniqueness, queries original completion-day account/world usage, recent grant time and same-partner receipts, checks current shared incident/sanction eligibility, then applies the strict M13-01 decision. Denied sources mint nothing. Same source/day cannot move to another day through client timing. Out-of-order completion observations earlier than the last granted source conservatively deny; late work is not retried into a higher cap. Current safety closures withhold new rewards without preventing private timer history. Replays of already committed sources return the same private balance and grant nothing further.

One SQL transaction inserts the immutable positive grant and idempotent cosmetic entitlements when lifetime XP crosses configured thresholds. XP is not spent. Existing casual is always a free baseline. No unlock automatically equips an outfit or creates a staff/shift role; M13-03 owns those checks. Entitlement insertion failure rolls back the ledger/source transition. Unique ledger/entitlement keys and account serialization prevent retry races, cap races and duplicate unlocks. Exactly-once refers to committed PostgreSQL business effects, not arbitrary delivery or user reading.

GET me/progression and own export expose bounded100 grant rows with truncation,current private XP and entitlements. Source IDs, partner IDs, fingerprints, room/seat/session data and other accounts' histories are absent. Minimal grant history/entitlements remain for the account lifetime to preserve replay protection and balance; owner erasure cascades both. Updates and truncate are rejected by the ledger trigger; database administrators remain trusted, and no hostile-DB-owner tamper certificate is claimed. M13-05 will implement compensating reversal rather than rewriting grant rows.

Partner abuse metadata lives in a separate private FK-linked table so erasing either account removes all pair links while retaining the survivor's earned XP. It is excluded from public/peer projections. Maintenance deletes at most100 partner receipts older than two days, beyond the maximum24hour observation window; raw partner IDs do not become permanent immutable ledger metadata. Account reset/collusion detection is bounded by caps rather than an identity-proof guarantee. Retention choices require owner review before public rollout.

Migration0023 creates ledger/entitlements/partner receipts and append-only mutation guards. No legacy data import or destructive down migration. Rollback disables progression policy/consumer while preserving the ledger,private export and replay identities; cosmetics remain subject to independent appearance policy. All real rollout flags stay OFF. Actual focus/hospitality adapter integration uses synthetic world fixtures; no real Deadline/Maid deployment is implied. No currency,trading,paid attention,leaderboard or social-contact reward exists.
