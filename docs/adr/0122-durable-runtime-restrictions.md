# ADR0122: durable operator runtime restrictions

Date: 2026-11-06. Status: accepted for the N07-03 runtime slice; complete-task acceptance remains pending.

Add a durable restriction layer to the existing versioned world runtime. The effective policy intersects immutable release entitlement, the current accepted Git runtime policy and operator pauses. The operator can pause an installed/entitled world or enter world-access maintenance. Removing a pause cannot grant installation, entitlement, communication capabilities, a Git-disabled world or an independently closed safety surface. Legacy installation profiles expose unsupported controls and retain their current owner and defaults. No runtime command writes a policy file, deploys an artifact or provisions a principal.

Store desired restrictions per environment, bound to a digest of the parsed immutable release policy, with an independent optimistic revision. The operator singleton's fresh transaction boundary checks MFA, Origin/CSRF, fixed actions/reasons, request-key replay and a durable hourly budget. Desired state and immutable HMAC before/after audit commit together. Audit uses the database clock and contains only policy metadata; no player identity, credential, approval reference or file path is retained or returned by this projection.

Positive authority is fenced after the SQL/audit work and before the parent transaction's final authorization/COMMIT. Pending fences survive concurrent file reloads; a reload cannot clear another in-flight fence. After transaction settlement, a serialized reconciliation reads canonical state and applies it through the existing registry. Failure rolls back desired state and restores the previous policy; a lost COMMIT acknowledgement reconciles what actually committed. Exact replay never reapplies an old desired snapshot over a newer command. World hooks and visit removal run from canonical state after COMMIT, preserving current consent on rollback and requiring a fresh visit after a real closure.

Expose desired revision separately from applied revision and APPLIED/PENDING/FAILED/STALE projection status. A committed desired change does not imply successful projection. The API's tracked three-second reconciliation retries pending/failed application without another mutation or audit entry. Background cleanup, identity/privacy and independent safety withdrawal remain available during world-access maintenance. The durable worker keeps its separate entrypoint and never constructs this room runtime.

On restart, apply persisted restrictions before world access. A different immutable release digest makes existing restrictions stale and keeps every world closed. An audited rebind adopts the running release while forcing maintenance on; recovery is a separate command. Editing the release file does not change the running process's captured entitlement. Missing or invalid runtime policy, invalid stored state or reconciliation failure cannot open a world.

Migration 0043 is additive, preserving the first 42 SQL files and the single journal; strict 43 compatibility is required. This design assumes the existing one-room-owner deployment and application-mediated control writes. Direct database mutation and multiple active API owners are outside this qualification. No production migration, public/store release or distributed-control guarantee follows from local verification.
