# Kubernetes preparation and target inventory

N04-01 prepares two Kustomize overlays, `infra/k8s/overlays/{staging,production}`. They are deliberately **not deployment eligible**. No application image has been bound to these overlays, no ingress is open, and no actual server inputs are implied. [Prerequisites](../../infra/k8s/prerequisites.json) are declarations, not an inventory marked healthy.

Run `pnpm k8s:validate`. It installs checksum-pinned Linux amd64 tools into ignored private artifacts when missing, verifies cached binaries/schemas on every run, renders both overlays, decodes the actual YAML offline with pinned kubectl and an empty kubeconfig, compares the output with the constrained source graph, and applies source policy plus strict Kubernetes schemas. Missing schemas, skipped resources, altered cached executables and unsafe policy changes fail. Two malformed resources must also be rejected by the real schema validator. `pnpm infra:check` includes this gate, so existing core CI runs it. No default cluster context is read by this command. Reports/log hashes stay under private `artifacts/k8s-validation/`.

The lock uses Kustomize5.8.3, kubeconform0.8.0, kubectl1.37.2 and immutable Kubernetes1.37.0 schemas at `102361970337d65537d40141dc29b991b8e95786`. k3d5.9.0 is pinned for the separate local fixture. These are preparation tool pins, not an application release or a claim of signed supply-chain/CVE qualification. New host platforms/server minors need their own pins and verification. No npm dependency or application runtime version changes here.

Each overlay renders two Deployments, two ClusterIP Services and five NetworkPolicies. API has one replica, Recreate, live/ready separation, bounded startup probes and20s termination grace around the existing12s process drain. Web may surge by one replica. Both run without root, capabilities, privilege escalation, writable root filesystems, host networking or mounted service-account tokens. Writable paths are bounded tmp/cache volumes. API starts `dist/main.js`, keeps its default durable dispatcher role and never starts a second owner or a worker. No autoscaler or new worker workload is installed.

Application limits are API1000m/768Mi and web400m/512Mi. Peak accounting includes a second web replica and a200m/512Mi migration reserve:2000m and2304Mi, within the provisional2000m/4096Mi application ceiling. No migration Job is installed in this slice. Cluster/control plane, OS, PostgreSQL, ingress, storage and backup costs/resources are excluded. This is not a server sizing or player-capacity result.

Namespaces, service accounts, policy ConfigMaps, session/database/registry Secrets, PostgreSQL and PVCs are external prerequisites. None is in application prune ownership. The deployment references required objects and fails to start when they are absent; a successful dry-run does not prove their contents or credentials. Environment policy must match staging/production, use reviewed release/runtime/safety files and preserve all world/media/operator/consent gates. No fixture activation or Secret value is committed. Migration hooks in N04-03 must consume prerequisites that already exist before PreSync, rather than relying on Sync to create them.

Network defaults deny ingress/egress for VLP pods. Allowances cover only selected CoreDNS pods, web→API4300 and API→the selected PostgreSQL pods in the environment's external data namespace. Web has no ingress allowance yet; no public Ingress, NodePort or LoadBalancer exists. A different DB topology needs a reviewed narrow peer rule. NetworkPolicy objects passing schema validation do not prove CNI enforcement. N04-03/N04-04 must exercise actual connectivity and deny paths before opening a reviewed private ingress route.

The API still trusts one exact `TRUSTED_PROXY_IP`. It comes from external configuration; do not substitute a whole Pod CIDR or trust every forwarded header. A real controller/proxy boundary must be observed and tested through HTTPS/WSS, with spoofed headers/Origin/CSRF and private routes, before deployment eligibility. Controller presence alone is insufficient, and these overlays add no extra proxy by assumption.

For an explicitly authorized target, run `pnpm k8s:preflight <staging|production> <private-kubeconfig> <explicit-context>`. This read-only inventory requires an explicit private configuration file and currently schema-qualified1.37 server minor. It selects node version/architecture/readiness and ingress-class counts; it never reads Secret/ConfigMap values or falls back to the user's default context. It reports `INVENTORY_ONLY`, with CNI enforcement, ingress qualification, registry pulls and external prerequisites still unverified. Inventory declarations never authorize a deployment or release. No real target has been supplied by the repository plan.

Image references use reserved `registry.invalid/...:release-required` sentinels. They are not fake digests or tested artifacts. Preparation policy rejects replacing them with arbitrary tags or self-declared digest strings. N04-02 owns verified release-set binding/promotion; N04-03 owns full sync/hooks/drain and target rules; N04-04 owns an actual authorized staging deployment. No Argo Application or automatic promotion is activated here. Rollback of this preparation is a Git revert; do not delete persistent resources or down-migrate data.
