# Maid local compatibility and recovery

This runbook covers owner-authorized offline integration only. Original Maid source,processes and data remain independent. The selected foundation has health/catalog schema and contracts,but no prior playable Maid room to restore. All real rollout/public gates stay OFF.

The recipe-aware adapter initially used world/policy/workflow1.1.0;the native room advances world to1.2.0,scene1.0.0 with unchanged policy/workflows1.1.0. Recipes are immutable snapshots on canonical orders. A private assigned-worker challenge expires60seconds after the minimum preparation deadline and is bound to order,assignee,course,version and readyAt. Expiry is checked again after receipt SQL work,before commit. Ready retries return the current recorded outcome;Stop/requeue/reassignment/restart invalidates old authority. There is no separate raw nonce/attempt history to migrate or erase.

Migration0038 records the serialization compatibility boundary with a column comment and journal entry. It rewrites no player row and adds no table. Older strict workflow readers cannot parse a persisted recipe field;their older exact migration manifest must therefore fail readiness. Do not delete the marker,downgrade the API or drop order/history/withdrawal data to make an older candidate look compatible.

For local closure,set the existing `maid` world flag false in an owned development/test flags file and use the established flags-manager reload. Retain current recipe-aware code. Check that the own membership is gone and old source commands fail. Own unfinished-order withdrawal and independent voluntary-work Stop stay available;normal bounded recovery clears stranded work. Already served service remains eligible for its original customer's independent acknowledgment. Re-enable only through a fresh confirmed visit and voluntary role choice;old membership or preparation nonce does not authorize new work.

If removing `LOCAL_MAID_WORLD=1`,also remove the `maid` key from the owned flags file,or omit `WORLD_FLAGS_FILE`;the strict registry rejects unknown keys. Original source rows remain untouched,and no source cookie becomes City login proof. Past served/completed workflow history remains readable on compatible code. Old timed unserved work is handled through withdrawal or bounded recovery after the original visit ends,not rewritten into a recipe challenge.
