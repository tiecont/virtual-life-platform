# PostgreSQL admission preparation

N09-02 adds an **unwired** service port in `apps/platform-api/src/admission/store.ts` and additive migration0044. Existing web/mobile/room/travel behavior has no admission hook. New policy defaults are hard0/target0/paused; no recommended CCU is asserted.

The trusted caller supplies the actual single RoomAuthority assertion and that room-owner lifetime's stable epoch. Call `recover()` before use; false means another bounded batch is required and ordinary calls remain unavailable. Never generate a different epoch for each adapter or request, or reconcile while the previous in-memory room owner is still live. A new owner never restores memberships, seats, room entitlements, consent or focus state from a slot row.

`command(sessionCredential,input)` supports enqueue/claim/leave with strict contracts, version checks and durable idempotency. `own()` returns only the authenticated account's ticket/offer/lease. `offer(requestId)` and capacity/recovery/transport methods are internal owner ports, not public endpoints. The internal offer result includes accountId solely for delivery by a future trusted adapter. HTTP Origin/CSRF, native-ticket authentication, polling budgets, privacy-export registration and room/travel lifecycle binding must be added and qualified before activation. The existing account-delete path already cascades all entries/receipts.

FIFO uses a unique sequence, including deterministic ordering for simultaneous arrivals. Duplicate enqueue never refreshes queue position or ticket deadline. Ticket TTL defaults900s, offer10s and grace30s; missed offers or expired grace release their counted slot and require a fresh enqueue at the tail. ACTIVE stays counted until an authoritative release or actual owner replacement. Travel must reuse that slot; room/booking capacity stays separate. Pausing denies new offers, while already counted offers/grace can complete within their deadline. Lower target drains without kicks; pending hard reduction settles only when occupancy fits.

Every transaction performs bounded expiry (100tickets and100receipts) using DB time. Expired rows beyond the batch remain counted conservatively; a rejected transaction rolls cleanup back. Reads/commands eventually advance cleanup when committed; no background worker or autonomous timer is deployed. A future owner scheduler must preserve these limits. Receipts older than seven days may be pruned; old enqueue replay can create a fresh WAITING ticket, never restore ACTIVE. Claim/release versions and fresh server IDs prevent old receipts from affecting another lease.

During failure, stop grants and retain canonical DB state. Do not compensate an unknown COMMIT acknowledgement with an unconditional release/regrant. Retry the exact request: receipt plus current own state determine the outcome. Owner loss denies further operations; replacement recovery preserves waiting tickets and removes obsolete owner leases in batches. Existing identity sessions remain intact, but users reenter worlds through normal authority/consent checks. Do not delete or recreate admission tables to recover.

Run implemented `pnpm test:admission`, applicable integration/security/type/static checks and strict44 image readiness on a disposable local database. Actual command results and source/artifact hashes belong in the task audit; this runbook does not itself assert a PASS. No staging load, capacity, native device, public deployment or store qualification is implied.
