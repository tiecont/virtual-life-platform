# Account-scoped waiting screen preparation

`/queue` mounts the shared `QueuePanel` through the existing platform request/navigation/identity port. It uses HTTPS-style HTTP requests, never a waiting gameplay socket. Public text shows only the viewer's own position/offer/lease, a server-backed countdown and an unknown ETA when no measured range exists. Rank is not converted into an invented wait time. Room seating/invitations remain independent.

The additive queue view/receipt contract identifies only the authenticated viewer; it excludes other accounts, capacity totals, owner epochs and internal allocator output. The local API preview is explicitly `LOCAL_ADMISSION_UX=1`, defaults0 and is rejected in production or versioned release profiles. It shares the actual singleton RoomAuthority and a stable AdmissionStore lifetime epoch. Startup performs bounded recovery or fails closed; there is no automatic allocator timer or room/travel hook in this UI slice. The original hard0/target0/paused policy is unchanged. Public/runtime activation still needs the capacity/admin/lifecycle/fault gates; do not turn this development flag into a production override.

GET/POST `/v1/admission` require the existing signed, live web session; writes also require exact web Origin and CSRF. Unknown query selectors are rejected. Per-IP300/minute and per-session30/minute limits bound polling and mutations; store-level command budgets and transaction/owner guards remain. Responses are no-store,429has Retry-After. No public offer, cap, account-select or disconnect endpoint exists. Reconnect only confirms the viewer's already existing bounded grace state. Native session authentication/transport is separate N10-03 work; Android login is not supplied by this web-cookie adapter.

The controller polls normally every3.2–4.8seconds, uses jittered exponential outage backoff capped60seconds, respects60seconds for429and bounds each HTTP attempt to8seconds. Manual refresh has a2.5second floor. Background/disposal abort requests and pause polling/countdowns. Return checks current server state before enabling actions. A monotonic countdown uses server timestamps; its zero disables claim but does not manufacture an authoritative expiry. Only an explicit click claims/reconnects. If a previous ticket disappears, text allows both expiry and cancellation on another screen rather than inventing the cause.

Unknown mutation acknowledgements retain the same body/requestId for explicit retry and block another action. The current own state is read independently; an idempotency receipt never resurrects an obsolete grant. Identity changes immediately clear private display/pending intent, invalidate in-flight generations and refetch identity; old identity/own/mutation responses cannot restore the previous account. No credential/ticket is stored in localStorage or metrics. Multiple tabs rely on the database's one-account entry and canonical snapshots, without a fragile browser leader.

Implemented checks: `pnpm test:admission` includes contracts/model/store/actual HTTP and controller cases. Build the current portal/API/packages with `pnpm build` before `pnpm test:queue-ux`; the latter runs desktop and Chromium mobile against actual local sessions/HTTP/PostgreSQL and the shared Next UI. The dedicated fixture enables the local preview, uses synthetic capacity1 and directly seeds an offer to isolate UI/claim behavior. Allocation fairness/concurrency is tested separately through the trusted store port. Actual commands/results must be read before PASS; this document is not evidence that a run succeeded.

No native-device/physical performance, staging queue storm, recommended CCU,3D visuals, human usability, privacy-export activation or public distribution is qualified by the queue UI. Native reuse still needs N10-03; runtime rollout still needs N09-04/05 and the deployment gates. Disable the preview to retain the existing404/friendly try-later UI; preserve canonical tickets/receipts/SQL, never wipe them for rollback.
