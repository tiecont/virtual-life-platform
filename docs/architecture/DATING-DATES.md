# Synthetic private DateRoom

M20-04 is a closed native prototype built on the existing private matcher. Normal development/production has no positive provider or dating liveness observer. It installs no generic world module or public Room. Real approvals/flags remain OFF;M20-07 stays BLOCKED_EXTERNAL.

GET `/v1/dating/dates/:proposalId` accepts only the currently accepted pair's original registered sessions,current synthetic proof/profile/safety/block and deadline. It initially returns WAITING,own consent/version and no partner projection. Each participant explicitly POSTs `/enter` with expectedVersion,consent:true,Origin/CSRF/idempotency key and an authenticated connected original session. Two choices activate a private timed conversation. Equal-version concurrent choices may return409;refresh before another explicit choice. The original accepted lease is never extended. Read/enter responses disclose only the partner's chosen neutral private alias after both consent;no city nickname,global account ID,topic list,friend status or general presence.

This is a dedicated SQL DateRoom rendered with native controls,not a generic RoomService membership or Socket.IO room. Generic dating room directories,room.join and travel preparation are denied even to otherwise eligible actors. Ordinary reviewed-adult travel remains supported outside the isolated dating product. There is no forced teleport or location disclosure and no Pixi dating-world claim.

POST `/chat` accepts only configured hello/thanks/need-help/bye keys. There is no free text,attachment,media,peer selector or client time/role authority. One new message per2seconds,20/date and60/hour are account-persistent budgets. Receipts contain random IDs/HMAC fingerprints/quota times only. A committed receipt may reach a volatile feed of20recent messages within at most100date feeds;it promises recording,not delivery. No chat content is stored in SQL or general evidence cache. Manual current observations expire<=3seconds including request elapsed time. The UI labels observation/state and requires checking again rather than showing old fields indefinitely.

POST `/v1/dating/date/leave` reuses independent matching Stop. It works while a positive request is pending and after positive key/flag/proof/report availability is lost,subject to current general authentication/Origin/CSRF/key and transport budgets. Leave/private block have separate IP/session transport budgets:exhausting positive checks/messages cannot consume their allowance. It withdraws the current allocation;historical same-key receipts do not override a later independent new choice. Profile save/withdraw/expiry,block,erasure,deadline/current proof/session/safety loss and maintenance end contact without automatic requeue. The SQL order is positive mutex→captured sorted accounts→proposal→date/receipt;negative owner callbacks use proposal→date and no new peer/global/Room-owner locks. Existing3second recovery checks20proposals+20queues fairly and cascades ended date state;cleanup remains100rows/table/batch.

Server-owned connection generations bind date consent to original-session liveness. A remaining authenticated tab preserves that generation;last-socket loss or process epoch change prevents reconnect from restoring consent. The lost-generation callback cannot terminate a later explicitly consenting new generation. Sockets carry only existing identity control messages,no dating data or broadcasts. Positive commands still check the current DB session;the liveness observer is never eligibility authority.

POST `/dates/:id/block` resolves a previously entered own date internally within24hours of first entry. It creates a platform Social block and terminates date work in the same transaction. Private blocks omit newly learned peer IDs/labels from general block lists,exports and friendship notifications;normal general blocks preserve their existing contract. Own Social export gives only timestamps for private blocks. Already independently disclosed general relationships remain general. A dedicated opaque private block-management UI is not implemented in this slice and needs privacy review before any real operation.

Block acknowledgment means the original request was recorded. A same-key retry does not override an explicit later unblock in another context;the UI therefore makes no claim that a historical receipt describes current block state. A fresh explicit block remains available. Unblock or old retries never reopen the ended date.

POST `/v1/reports` with source `{kind:'private-date',dateId}` needs actual started own date provenance within the same24hour window. It remains independent after Leave/block/proof withdrawal. It never needs public global presence or a client-supplied peer ID. Shared Safety encrypts the allegation,requires assigned/conflict-free scoped review and creates no automatic sanction. Date-only room ejection uses that opaque Date ID;world/platform restrictions still apply. The UI offers one-click consent-violation reporting with no invented transcript. Historical reporting does not authorize reading a former partner profile/messages or restarting conversation.

Own Date export is bounded100lifecycle summaries without peer/date IDs. Account erasure invalidates the shared match/date before FK cascades. Proposal/date history and date receipts keep24hours with bounded cleanup;negative matching fences retain90days. No guarantee is made about lawful retention,backups,real human18+assurance,operator coverage or production safety. Migration0035 adds dates/receipts and a default-true Social disclosure field;disable positive prototype use for rollback while retaining independent safety/privacy handlers.
