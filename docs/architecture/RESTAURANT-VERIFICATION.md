# Restaurant local acceptance

M18 implements an independent,default-OFF virtual Restaurant using the existing Room,Events,Hospitality,Social,Invitation,Reports and Travel owners. It supplies no physical food sale,media playback or real operator account. It does not integrate the legacy Maid application. Technical local task acceptance and public release are separate.

M18-01..05 evidence is recorded in `m18-{scene,booking,roles,courses,private}-checks.json`. The M18-05 stable root check passed7governance,214unit,368integration and all builds. A later actual city-discovery case passed separately;there is no369-test full-run claim. M18-06 changes test tooling,benchmark scripts and documentation only;production application source/assets/migrations remain at that verified revision. Its actual commands are recorded in `m18-acceptance-checks.json`.

The final Restaurant browser profile covers original scene/identity/chairs,asset failure,native table booking/confirmation/check-in,individual party consent,private friend offers and separate travel/join,confidential contact reporting/blocking,independent Stop during pending replies,voluntary Server/Cook authority and all three real-time courses followed by one customer acknowledgment. Two independent browser contexts submit holds through a shared interception barrier to one actual table. The backend returns exactly one201 and one409;SQL has one active allocation and one checked-in holder. The loser acquires no booking;neither holder check-in nor party size creates guest attendance or a chair. The winner completes check-in through native keyboard controls while the actual scene asset is unavailable. These cases run on desktop and an emulated mobile viewport.

Actual screenshots and measured target/contrast rows are retained under `m18-acceptance-visual`. This is a local browser regression,not a full screen-reader/device or WCAG certification.
