# Gated ephemeral room chat

M08-02 implements an authenticated backend pipeline only. Chat is OFF by default, including the normal development sandbox. Only trusted application construction can enable it in development/test; production always denies it. World flags, declared chat capability, admission and policy remain independent requirements. No chat UI, DM, history or public activation is supplied.

`chat.send` has a strict versioned room-own-command envelope and a text/canned/emote union. The server derives actor, socket, room, membership and audience. Text is bounded, NFKC-normalized, stripped of format characters and inspected before delivery. HTML delimiters and unsupported controls are rejected. The local moderator approves only curated benign Vietnamese/English phrases, rejects limited explicit abuse and holds unknown/contextual content as rejected for delivery. It is not a general classifier and there is no human review queue yet. No classifier outcome automatically sanctions an account. Semantic display-name moderation remains an M08-06/public safety gate; existing profile syntax/visibility validation is not semantic review.

Shared account limits are 6 new messages/10 seconds, 2 in-flight/account, 64 globally and 8 per socket, in addition to existing gateway limits. At most four underlying moderator workers run; a 500 ms deadline aborts a provider request but retains its slot until the provider actually settles. Throws, unknown decisions and timeouts fail closed. Approved server-authored canned IDs/emotes can continue only when the context permits the explicit fallback. Denied text is never silently substituted. Provider JS is trusted; CPU-blocking synchronous code is not isolated by this asynchronous deadline.

Before publishing, RoomService rechecks owner generation, authenticated session, active membership, world/capability and current viewer projections, including bilateral block/privacy. Tests block after moderation starts and prove withheld delivery. This does not recall a message already queued on the network or establish linearizable privacy across every possible external write race. Sender profiles come from the existing authorized profile projection; no client-supplied recipient/sender role is trusted.

Delivery is volatile, best-effort and ephemeral. A successful ACK means an event was accepted, not that every recipient received it; disconnected/nonwritable observers are dropped with aggregate-only diagnostics. There is no offline history. Success receipts retain metadata/fingerprints only, bounded to 10,000 entries for five minutes; matching pending retries share one broadcast, conflicts fail. Deduplication is in memory and does not survive restart. No raw ordinary/rejected chat is persisted or logged. Shutdown aborts inspection and prevents late acceptance/emission.

M08-03 adds an explicit separately keyed report opt-in: up to 1,000 approved message delivery attempts may be retained encrypted in volatile memory for five-minute recipient-bound report references. Only a submitted report persists its minimal encrypted evidence. There is still no durable ordinary/rejected chat history. See REPORTS.md for eviction, audience, key and deletion limits.

Policy JSON is validated before allocating app resources, copied to the built API's safety directory and loaded there; source execution falls back to the repository config. Missing/invalid configuration fails startup. Existing clients keep their room contract; chat is an additive registered command.

Actual verification is in `docs/agent/evidence/m08-chat-checks.json`. Synthetic tests use a known policy context with a sandbox world definition, not an integrated/activated Maid world. M08-03..06 still need confidential reports/encrypted evidence, audit/RBAC, sanctions, appeals, moderator UI, retention and broader false-positive tests. Named coverage, privacy/retention review and public approval remain absent.
