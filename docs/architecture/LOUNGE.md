# Moonlight Lounge

M19-01 is an independently authored local all-ages text/visual venue at `/worlds/lounge`,locally verified in M19-01. It reuses Room/Identity/Scene/Events/Reports owners. Activation requires both nonproduction `LOCAL_LOUNGE_WORLD=1` and an independent registry flag;production rejects this local option and real rollout stays OFF.

World1.3.0/scene1.0.0 has ten reachable exclusive audience chairs,two circulation places within twelve room places,a virtual mocktail counter and an original raised stage. The closed stage is a solid collision zone with no audience seat or public floor-entry command. M19-01's audience stage occupancy remains zero. M19-02 separately allocates at most one logical text/visual performance per room;starting it does not move an avatar,change a membership or claim a chair. Choosing an audience view or outfit grants no performer/host/staff permission.

The new stage collision kind is interpreted by the same authoritative path checks as every solid zone. Both invalid canvas destinations and forged socket movement are rejected;native chair controls remain the accessible alternative. The original renderer theme draws geometric curtains,crescent/stars and decorative mocktails. There is no audio/video/player,external stream or real alcohol. Low-motion behavior and actual asset-failure fallback remain shared scene behavior. Source provenance is served at `/assets/lounge/provenance.json`;releaseApproved remains false. Existing Library/Restaurant manifests update only the shared renderer fingerprint.

Read-only native Text and visual sets consumes the Events catalog's current phase,IANA labels and capacity. At most five listed sets are displayed;private sets remain owner-filtered. No sample live schedule or real operator is provisioned. Reads have8second deadlines/30second observation expiry and identity/hidden/offline invalidation. Confirmed empty results are distinct from failed or expired observations. A listed/LIVE event does not open the stage,admit anyone,reserve a chair or grant performance permission. Browser schedule SQL rows are rendering fixtures;actual authorized scheduling/phase/private filtering uses the owner API in integration.

The native Stage controls use current registered per-event performer grants and event-organizer or scoped moderator authority. The room FIFO holds at most ten open requests including any offered/active slot. Queue consent,host offer and performer acceptance are separate actions. Trusted policy clips thirty-second offers and sixty-second slots by current session/grant/event authority. Host/moderator revocation and independent own Stop work outside admission. Stop advances a durable consent revision;old keys and late UI replies cannot restore consent. Five-second stage observations expire to unknown;mutations use eight-second request deadlines and exact-key uncertain retries. Views disclose anonymous occupancy and no peer identities;operator controls expose opaque slot state only.

Events owns additive0030 consent/slot/receipt storage and observes event closure in the original transaction. Block also closes relevant contact atomically. Fair20-row recovery checks role/session/visit/restart/world/safety loss on the3second scheduler;disconnect ends performance at the next observation without automatic reconnect restoration. Backlogs need multiple batches. Every positive command reauthorizes. Exports are bounded/private;account/event deletion cascades history and deleted offering-host proofs are cleared. Stop receipts older than90days are purged in100row batches. See ADR0062 for locks,deadline failure recovery and the physical stage boundary. Retained dev DB is0030/stopped;real flags and real staff provisioning remain untouched.

Refusal,block,outside-room customer withdrawal and independent staff Stop retain shared semantics;retries reuse the existing unique course/completion/outbox ledger. No alcohol,payment,tip,score or automatic reward exists.
